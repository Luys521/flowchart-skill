# 《流程表》规范模板

> 这是 flowchart-skill 的**唯一事实源**模板。AI 提炼流程、渲染出图，都以这份表格为准。
> 校验用：`python flowchart-skill/scripts/table_to_dsl.py --check "output/<名称>/flowtable.md"`
>
> 文件分**三区**（D-59）：本头部 YAML 是身份区（id/level/parent/refs/description）；
> 下面两个小节是配置区（布局与颜色）；「## 流程表」是逻辑区。
> **背景散文（项目/流程范围/裁决依据）不写在流程表里**：判断依据由节点上的 ⚠/⚠? 留痕承载，
> 一切规则都在流程中体现（D-58）。

## 列填写规范

> 层级 / 来源 / 显性判定 / 校验的完整定义见 `references/flowtable-spec.md` §2 的**字段登记表**；
> 这里只讲每一列**怎么写**，逐条对照上表。

- **项目运作阶段**：阶段分组名（如 `读材料` / `落表` / `回流`），仅用于归类，不参与校验。
- **节点编号**：唯一标识。主干用纯数字（`01`、`02`…）；两号之间插入用字母后缀（`03b` = 03 与 04 之间插入的第 1 个）。
- **节点名称**：动宾短语；判断节点以 `？` 结尾（如 `入口判定？`、`结构校验？`）。
- **节点类型**：`开始` / `结束` / `任务` / `判断`（四种，**形状是类型的可见形式**：矩形=任务、菱形=判断、
  胶囊=起止。判断=菱形，会强制校验分支完备；`结束`可以有多个——每个结局一个）。
- **输入**：这一步**被消耗或改变**的东西（材料、单据、上游产物）。不涉及写 `—`。
- **依据**：这一步**凭什么这样做、这样分**——条款 / 标准 / 判据的出处（ICOM 的 Control：不被消耗，只决定能不能做、做到什么程度）。
  **写得出来就写这里；写不出来就在「节点描述」以 `⚠` 开头**（两者都空 = 没想过，校验会点出来）。**判断节点的依据最要紧**：它就是分支标签背后那条判据。
- **输出**：这一步交出去的东西（文件、决定、回执）。不涉及写 `—`。
- **执行主体**：主体名任你定义（角色名 / 部门名 / 公司名皆可，`用户`、`AI`、`脚本` 是本范本的取值）；同一张图内主体名固定。配色默认按出现顺序自动分配，要**钉住**就在「## 主体配色」小节表里写 hex（子流程自动继承，跨层不一致会被拦下）。
- **执行者**：纯净称谓（岗位名 / 角色名 / 工具名）。**与执行主体同档**：主体写 `AI` 就填 `AI`（工具名写进「节点描述」），主体写 `脚本` 才填具体脚本名（如 `build.py`）；协作写 `双方共责`。
- **行动所需时间**：如 `1-3个工作日`、`30个工作日`；不涉及写 `—`。
- **下个节点**：
  - 单链：`→03`
  - 结束：`—`（**只有「结束」能填**——一张图可以有多个结束，每个结局一个）
  - 多分支：每分支 `标签→目标`，分支间用 ` ｜ ` 分隔；`回` 表示回环。例：`通过→05 ｜ 不通过→回 03 修正`
  - 判断节点**必须列全每个可能结果**（即分支完备，对应 H4），且**每个分支都要带标签**
  - **任何节点都可能有多出口，不只判断节点**：判断的多出口是**排斥**（选一条走），其余类型的多出口是
    **并行**（全都走），标签只是路线名——判据是**类型**，不是标签（见 flowtable-spec §2《类型登记表》）
- **节点描述**：做什么 + 补充说明 + `★` 关键点；**AI 推断的内容以 `⚠` 开头，必须业务方拍板的以 `⚠?` 开头**（渲染后该节点为两档虚线描边）。

> **显性判定**：`输入 / 依据 / 输出 / 行动所需时间 / 节点描述` 这几列**由用法推导**——本表至少有一个节点填了它，才算本表的显性字段；
> 全表 `—` 的字段不要求填、也不进悬浮框。上面的范本演示了两种：**「行动所需时间」是显性的**（脚本工序填了 `1-2 秒` 这类秒级时长，AI / 人工序留 `—`），**「依据」在 `07 问并收答复` 那行是 `—`**——那一行的依据确实不存在，不是漏填。

> 目标效果：这张表被 AI/同事看一遍就能准确画出流程图，且任何分支、时限、依据都能在表里求证——这就是"想清楚"的标准。
