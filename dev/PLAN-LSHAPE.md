# PLAN-LSHAPE：前向对角 L 的两种实现（枚举式 vs 推导式）

## 为什么要比

D-161 / D-162 把「前向对角干净 L」补成了四档，但**实现是白名单式的**：四行手写的
`cands.append(...)`，靠"排在 `_candidates` 首位 + `_route_pending_edges` 取第一个不冲突的"生效。

全仓实测（59 张表 / 1610 条边）：跨列边**只有 12 条**（98.4% 是同列 spine），射程内
**12/12 命中、零例 Z 形**，跨 4 张表 —— 规则确实生效，但枚举之外的对角形态（**反向对角**，
`row_from > row_to` 跨列）不在内。三条不完全泛化见上轮评估：枚举式、靠优先级后门、
`path()` 的 `to_h`/`to_v` 对 jumpR 是死代码。

## 两条路线

| | A 枚举式（现状） | B 推导式 |
|---|---|---|
| 候选来源 | 四行手写 `cands.append` | 由**端口法线**推导 8 种组合 |
| 覆盖 | 前向对角（`row↑` 跨列）4 档 | 前向 + 反向对角，共 **8 档** |
| 方向合法性 | 由 `col_from < col_to` **隐式**保证 | 由首/末段是否沿端口法线**显式**判定 |
| 优先序 | 代码行序（读代码才知道） | `_L_PAIRS` 元组序（数据即顺序） |
| 现有语料行为 | 基准（已四面全绿） | **应当逐字节等价**——反向对角在语料里 0 例 |
| 加一种 L 的成本 | 加一行、易漏（D-162 就是漏出来的） | 不用改代码，改判据即可 |
| 风险 | 漏档（已实测发生一次） | 方向判据写错 ⇒ 生成"贴着节点边沿滑行"的畸形 L |

**B 的推导规则**（8 种 = 出口水平 × 入口垂直 + 出口垂直 × 入口水平）：

```
exit ∈ {left,right}   ⇒ 折点取**目标**锚点 x（横-竖，末段零长）
exit ∈ {top,bottom}   ⇒ 折点取**源**锚点 x（竖-横，首段零长）
首段方向 = exit 的朝外法线；中间段 = entry 朝外法线的**反向**（线是"进去"）
同轴的两个端口凑不出单折点（那是 Z 形/直线），排除
```

## 判据（B 怎么算通过）

1. **产物字节等价**：`dev/baseline/` 全树（自举 49 张 + workflow 10 张）sha256 与 A **逐字节相同**
2. **四面回归全绿**：contract / gates / invariants / e2e
3. **新能力**：反向对角的合成用例 —— A 走绕行，B 走三点 L
4. **反向控制**：把 B 的方向判据改坏（去掉法线检查），第 3 条**必须**变红

判据 1 是主判据：反向对角在现有语料里 0 例 ⇒ B 若与 A 不等价，说明推导式**多算出了
本该被排除的候选**（方向判据有洞），那正是要抓的。
