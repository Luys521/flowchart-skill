# 验证层（SKILL 自检）

这个 SKILL 的产物质量由**两道机器门禁**（结构校验 / 质量门禁）+ **一道自检留痕**（AI 自查，把推断处标到图上）+ **一个同步闭环**保证。
这层是**校验机制自己的校验**——在改脚本/文档/字典之后，确认这套机制还成立。它不参与出图，只在开发与维护时跑。

```bash
python dev/verify/run.py                 # 四个面全跑（改完东西就跑这个）
python dev/verify/run.py --only gates    # 只跑一个面
```

退出码 0 = 全过；1 = 有面未通过。中间产物落在 `.verify_tmp/`：**全过自动删掉，有失败就保留**，可直接翻现场。

跑套件**不留字节码缓存**：入口设了 `sys.dont_write_bytecode` + `PYTHONDONTWRITEBYTECODE=1`（后者也交给子进程），
所以 `dev/verify/` 与 `scripts/` 下不会长出 `__pycache__`——那是运行产物、不属于仓库内容（`.gitignore` 同样认定）。
代价只是每次 import 重新编译，这些模块都很小。

## 四个面各管什么

| 面 | 文件 | 回答的问题 | 典型用例 |
|---|---|---|---|
| ① 契约一致性 | `contract.py` | 文档说的和代码做的是不是同一件事 | frontmatter 与目录名一致；文档引用的路径都存在；文档里的命令行参数都真实存在；`visual-spec` 参数表逐值与 `dictionary.yaml` 一致；结构校验是 H1–H8、质量门禁是八项 |
| ② 门禁拦截 | `gates.py` | 坏的能不能拦住，好的会不会被误拦 | H1–H8 各一个坏例（报错必须指向具体节点）；H8 覆盖孤儿/死胡同/不可达/分支重复；长标签只软提示、合法回路放行；节点重叠要报；泳道槽位/左走廊/并行分支各一组；产物侧微残段与底色铺满各一组；**泳道底图的"该不该有"按底稿判**（单元四方向 + 泳道源渲染成流程样时 build 必须拦下，见 `ARCHITECTURE.md` 9.10）；`validate.py` 缺参数/路径不存在不许"假通过"、列号越界要给中文报错；改标签不许丢注解 |
| ③ 不变式 | `invariants.py` | 不靠"这次对了"，靠"永远对" | 全部坐标落格（复用 `validate.check`）；换 `PYTHONHASHSEED` 产物字节相同；`build` 幂等；离格值自愈；图例带内无节点无折点 |
| ④ 端到端往返 | `e2e.py` | 一条完整的活能不能走完 | `init` → 填表 → 结构校验 → `build` → 截图 → 注入改动 → `sync` 差异精确 → `--apply` → 再 build 幂等 |

## 改完渲染器要做什么

幂等检查**在临时副本里跑**（D-20）：它把 `examples/<样例>/` 的 `flowtable.md`/`<流程名>-flow.yaml`/产物复制到
`.verify_tmp/` 再跑两遍 `build` 比字节。**验证过程不碰 `examples/`**——那里放的是工作产物，
而用户在 `<流程名>-flow.drawio` 里的手工微调一旦被 `build` 覆盖就找不回来了（旧版会留在 `.<流程名>-flow.drawio.bak`，
但那是兜底，不是许可证）。

因此**改过渲染层后，必须显式重生成样例**——否则基线里的产物还是旧代码画的，而契约面
（① ②）与不变式面（③）要读它们：

```bash
# 事实源铺进基线目录，只 build 主表（细节见 examples/README.md）
cp -r examples/workflow/. dev/baseline/workflow/
python scripts/build.py <基线目录里那张临时表>
python dev/verify/run.py
```

**别加 `--no-layout`**：它按表序重排，会丢掉**只存在于 `<流程名>-flow.yaml`** 的手调列归属（D-18）。

## 怎么加一条用例

面② 最常加：往 `gates.py` 的 `BAD` 里加一行 `(用例名, 期望出现的报错关键词, 行列表)`，
或在新段落里用 `_lib.run(...)` 起一条命令再 `c.check(...)` 断言。

约定：

- **共享的东西只放 `_lib.py`**（跑脚本、断言收集、md5、路径、合成表的 `HEAD`/`row`）；各面之间互不 import
- **不要重写产品的检查逻辑**：`_lib` 已经把 `scripts/` 挂上 `sys.path`，
  直接 `import validate` / `from engine import load` 复用——验证要验的就是那份实现，
  另抄一份只会让两边一起漂移
- **用例自带合成表，不借 `examples/`**：样例是给人看的格式基准，用例的规模与结构该由自己钉住。
  借样例的话，样例一改就有一堆用例跟着红，别人还看不出该改哪边
- **每个要 `build` 的用例占一个独立子目录**：`build.py` 按约定把几何提示读作同目录的 `<流程名>-flow.yaml`、
  产物也固定叫 `flow.*`。几张贴在同一目录里会互相覆盖，**前一张的 `<流程名>-flow.yaml` 还会被后一张当成
  几何提示**（实测：并行分支用例就是这么被泳道用例的残留几何带偏的，报出"端口方向与走向矛盾"）
- 路径一律从 `_lib.SKILL` 推，**任何 cwd 下都能跑**
- 断言要写清"期望什么"：`c.check(rc == 1 and 'H4' in out, 'H4 判断单分支被拦')`，
  别只断言非零退出码

## 源码注释约定

这套代码**只有 AI 会读**（没有人类读者）。在这个前提下，注释的取舍与常规相反：

**写**——代码本身说不出来的东西：

- **为什么这么写**：`grow=-2` 是为了留安全间隙；`ensure_gutters` 兜底必须往外找、不能回落最内侧通道
- **不能怎么改**：哪一行看着多余、其实改了会破坏某个保证。这是 AI 最容易翻车的地方（"好心改坏"）
- **踩过什么坑**：某段逻辑的形状是被一个真实故障逼出来的，重写前先知道它防的是什么
- **跨文件的不变量**：如"`router` 主动避让与 `validate` 事后复检必须共用同一套几何谓词"

**不写**——纯噪声，且会腐烂：

- 这行在做什么（`# 遍历所有节点`）——代码本身就是最准的表述
- 参数类型、显而易见的控制流、对函数名的复述

**为什么"过期的注释比没有注释更危险"**：人类读者能靠直觉察觉注释与代码脱节，AI 不会，
反而**更信注释**——它看起来像人类意图的表达。于是留着的每条错注释，都会在下一个会话里被当成
"前人的设计决策"照做。

- **改代码必须同步改注释。** 两者不一致时以代码为准，并立即修注释。
范例：`writeback` 的 docstring 若还写着"节点语义取自对象属性"，而代码早已是"以流程表为准"，
下一个 AI 就会理直气壮地把这个决策改回去。

### 第三条：文档已经讲过的理由，不要在代码里再讲一遍

上面两条管"该不该写"，这条管**该写在哪**。2026-09-10 实测：脚本注释占 18.8%，
而最大的一笔不是"解释代码"，是**把 `references/` 已经讲过的理由抄了一遍**——
`writeback.py` 的 21 行 docstring 与 `drawio-loop.md` 第 2 节几乎逐句重合。
三轮处理后 **891 → 452 行，18.8% → 12.9%**。

**一条信息只有一个权威位置。** 代码里只留一句指针（形如"细则见某文档第 N 节"）：

| 内容 | 权威位置 | 代码里 |
|---|---|---|
| 规则明细（H1–H8、八项门禁） | `references/flowtable-spec.md` §3 / `visual-spec.md` | 报错文案里的 `H3` 就够，不列表 |
| 产品定位（"高级 mermaid"） | `SKILL.md` 开头一句 | 一句指针 |
| 回写三条保真规则 | `references/drawio-loop.md` §2 | 只写"不许违反哪两条" |
| 命令用法 | `SKILL.md` 命令表 | 模块 docstring 里 1 行「`--x` 做什么」可以留 |
| **决策历史（含被否决的方案）** | **`DECISIONS.md`** | `见 DECISIONS.md D-xx` |

反过来，**下面这些必须留在代码里**，删了就没地方说：`-6` / `-2` 这类魔法数的意图、
`continue` 让位给别的层的原因、跨文件共用同一套谓词的约束。判断标准一句话：
**删掉它，下一个 AI 会不会做出错误的"改进"？** 会 → 留；不会 → 移到文档。

**谁来守这条**：`dev/verify/contract.py` 只断言**归属**（文档级表述不许出现在脚本里）——那是可机械判定、
且不会误伤的。**"是否冗余"不设机械指标**：体积不等于冗余，行数上限分不出"必须留的 why-not"和
"该走的叙事"，当裁判反而会让"删掉有用注释去凑指标"变成正确做法。
**改法**：注释该不该留，用定期的人工/子代理通读判断（判据就是上面那句"删掉它，下一个 AI 会不会
做出错误的'改进'"）。2026-09-10 实测过一次：读完 `scripts/` 全部 19 个文件，**约四成注释被判"冗余或错位"**——
其中多是复述 `visual-spec` / `swimlane-spec` / `DECISIONS.md` 已有的理由。这些**不删，压成一句指针**。

⚠️ **一个教训**：那次审查里，子代理的**分类可靠**（抽验 3 条 C 判定全部属实），但它给的**行数估计明显偏高**
——因为被判 C 的多数条目本来就只有一行，"压成指针"省不下行。**别拿分类条数当省下的行数**：
分类说"40% 有问题"，实际只省下 12% 的行。要做体积预测，自己按条目实际行数算。
