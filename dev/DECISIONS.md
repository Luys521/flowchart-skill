# 决策日志

这里记**反转与取舍**——"曾经是那样，为什么改成这样"。它是"为什么现在是这个样子"的权威出处，
也是代码注释里 `见 DECISIONS.md D-xx` 那些指针的落点。

三条规矩：

- **只记改过主意的事。** 一次就定对的设计直接写进 `SKILL.md` 或 `references/`，不在这里占位。
- **每条 ≤16 行**：结论 / 曾这么定 / 为什么改 / 影响哪些文件。"改了什么代码"不记在这——
  那是 git 和工作区日志的事，别在三个地方各写一遍。
- **本文档有意保留旧术语与旧举例**（如"门禁①"、"光伏"）。它是历史记录，必须能原样引用当年说过的话，
  所以校验脚本对本文档豁免术语与领域词检查。同理，下文提到的**旧样例目录**（当年用真实业务材料做的
  那几张）在发布包里已不存在——`examples/` 只留自举的 `self-demo`。

## D-01 回写方向：流程表优先，不是 drawio 优先

**曾这么定**：`subject` / `executor` / `time` / `name` 全取自 drawio 的对象属性，只有 `stage` / `desc`
从原流程表补。于是同一行里跑着两种相反策略。

**为什么改**：这跟「流程表是唯一事实源」是反的。在流程表改了执行主体、没重跑 build 就 sync，
改动会被 drawio 旧值**静默回退**，而 diff 显示成 `X→Y`，看起来还像用户自己改的——最难查的一类错。

**结论**：语义列一律以原流程表为准，drawio 对象属性只当兜底（流程表里查无此 id 才取）。

**影响**：全仓搬迁 + `dev/_paths.py`（新）+ 8 个工具路径改指 + `verify/{_lib,invariants,gates,contract}.py` 换根；四面全绿 + 七道门全过，样例产物 sha256 与搬迁前**完全相同**（改名不改字节）。
## D-02 门禁② 的定位：从"人审卡点"改成"图上留痕"

**曾这么定**：第三步是"待确认清单（人审）"，且写明「**未收到用户逐条确认前，不得进入第四步**」。

**为什么改**：两条都站不住。一是**拦不住糊弄**——AI 自己代填一句"已确认"就绕过了，还制造出
"已经把关过了"的错觉。二是它**要求用户去读流程表**，而本 SKILL 的定位是"用户只对最终渲染图负责"，
中间产物他根本不会打开。

**结论**：不设卡点。AI 自检后直接渲染；拿不准的内容在「节点描述」以 `⚠` 开头，该节点渲染成醒目虚线
+ 悬浮说明，**让不确定显示在用户唯一会看的那张图上**。

**影响**：`SKILL.md` 第三步；`scripts/semantics.py`（`is_pending`）；`references/flowtable-spec.md` 第 2 节。

## D-03 术语：三道「门禁」改成"结构校验 / 自检留痕 / 同步闭环"

**曾这么定**：门禁①（结构硬校验）、门禁②（待确认清单）、门禁③（回写闭环），统称"三道门禁"。

**为什么改**：三道里**只有①真阻断**，②是 AI 自查、③是同步机制。编号体系一旦有一个成员不成立，
整个编号就是误导——读者会以为有三道阻断门。

**结论**：去掉编号，按性质命名。统称是「**两道机器门禁 + 一道自检留痕 + 一个同步闭环**」。

**影响**：18 个文件的全局改名。`verify/contract.py` 有禁用词断言守着，别漂回旧词。

## D-04 分支分隔符：收窄成 `｜` 唯一，"我全认"改"只认一种"

**曾这么定**：解析器同时接受 `<br>`、真换行、`；`、`;` 四种，本意是宽容。

**为什么改**：宽容的对象错了。`；`/`;` 是**内容字符**，会自然出现在注解里
（`不通过→回 03 修正；需技术复核`）。一旦当成分隔符，`通过→05；不通过→06` 会被当成**一个**出口、
**静默丢掉第二条**——不报错，直接少一条线。

**结论**：写出统一用 `｜`（U+FF5C），读入兼容 `<br>` 与换行；误用分号当场报 H3 拦下。
分隔符只在 `semantics.BRANCH_SEP` 定义一处（原先三处各写一份切分逻辑，迟早漂移）。

**影响**：`scripts/semantics.py`、`table_to_dsl.py`、`xml_reader.py`、`writeback.py`。

## D-05 检查的组织：从"按解析阶段堆"改成"三层"

**曾这么定**：检查混在 `build_nodes` / `build_edges` 里（它们是**转换函数**，检查只是副作用），
判定散在 3 个函数，还有 4 个检查点连 H 编号都没有。判断节点的规则分散在两个函数里。

**为什么改**：读代码看不出"判断节点一共要满足几条"。而且顺序成了偶然的产物——
① 判错会让后面连错节点、报一串指向错处的假错；② 能判的拖到 ③ 会被淹在连通性报错里。

**结论**：按 ① 节点层 → ② 类型层 → ③ 关系层 跑，范围从小到大。**层 = 运行顺序，H 编号 = 规则主题**，
两条正交的轴（所以没有重编号）。每层一个函数，② 的规则集中在 `TYPE_RULES` 表里。

**影响**：`scripts/table_to_dsl.py`（`run_checks` 统一入口，`main` 与 `writeback` 共用）。

## D-06 一个节点只报一条：跨层让步

**曾这么定**：各层各报各的，同一个节点挨两条。

**为什么改**：两句说的是同一件事时，报错越全越难读。节点一多，真正要看的那条被埋掉。

**结论**：孤立 > 孤儿 > 不可达只报最先命中一条；**结束节点**的"没人指向我"专名叫「不可达」，
不再叠一条泛泛的「孤儿」；**死胡同**由 ② 报、③ 让位；**目标编号写错**只报 H3，不再叠"没有出边"
（否则提示自相矛盾：写着「下个节点」应为 —，可用户明明填了东西）。

**影响**：`table_to_dsl.py`（`wrote_route`）；`verify/gates.py` 有「同一个节点只被点一次名」断言守着。

## D-07 `TYPE_RULES` 里不放"入边要求"

**曾这么定**：讨论过把每种类型的入边要求也放进规则表，让表"完整"。

**为什么改**："必须有人指向我"**不是这个节点自己的属性**，得看别人——归 ③ 关系层。
补进表的直接后果是同一个节点挨两条报错：无入边无出边的节点会同时吃到"孤儿"和 ③ 的"孤立"。

**结论**：不入表。表只放"只看自己就能判"的约束（个数 / 出边 / 分支）。

**影响**：`table_to_dsl.py` 的 `TYPE_RULES` 上方注释（含"别顺手补上"）。

## D-08 H 编号的家：从"盯脚本 docstring"改成"盯 spec"

**曾这么定**：`verify/contract.py` 用正则扫 `table_to_dsl.py` 的行首，要求 H1–H8 都在。

**为什么改**：这等于**逼代码里保留一份规则表**——代码的重复有一部分是测试亲手制造的。
H 编号是给读者看的规则主题，它的家是 `references/flowtable-spec.md` 第 3 节。

**结论**：断言改盯 spec；代码侧只要求三层函数 + `run_checks` 存在。脚本里那份 H→层映射表整段删除。

**影响**：`verify/contract.py`；`scripts/table_to_dsl.py` 的模块 docstring。

## D-09 举例的领域：从"其他流程图"改成 self-demo 自举

**曾这么定**：文档与模板里的举例用真实业务的片段（光伏 EPC、踏勘、某主体、技术经理…）。

**为什么改**：本 SKILL 不预设任何领域，而**示例是定位的证据**。带领域的例子会让读者（含 AI）
反推"这是给那个领域用的"，还会把该领域的结构预设（甲方/乙方这种二元主体、必然有现场环节）
带进别的场景。`templates/flowtable-template.md` 更严重——它被 `init.py` 直接复制成用户的第一份文件，那不是"示例"，是产品门面。

**结论**：产品文档示例一律取自 `examples/self-demo/`（SKILL 把自身工作流画成图）；
模板的示例表**逐字等于** self-demo。三个真实业务样例（光伏领域）保留但**降级为"泛化证明 / 学习材料"**
——跨领域样例是泛化性的唯一实证，删了反而变成"只能画它自己"。

**后续**：这三个真实业务样例已在 D-42 发布整理时移除，本条"保留为学习材料"不再成立——以 D-42 为准。

**影响**：`templates/`、`references/`、`SKILL.md`、`examples/README.md`；
`verify/contract.py` 有"领域词不许出现在产品文档"与"模板必须等于 self-demo"两条断言。

## D-10 注释策略：从"越详细越好"改成"预算 + 归位"

**曾这么定**：只有 AI 读代码，所以为什么、约束、踩过的坑全写进去——写成了散文。

**为什么改**：写"为什么"是对的，**但写的是 `references/` 已经讲过的理由**，一条信息占了两个位置；
结果脚本注释占 18.8%（最大一笔是 `writeback.py` 的 21 行 docstring，与 `drawio-loop.md` 第 2 节逐句重合），
每个文件读一遍都要付这笔 token。更要紧的是**被否决的方案只藏在注释里**——换个位置就看不见，
下一个会话会把旧方案重新提议一遍。抽成本文档，代码里的 why-not 才能退成一句 `见 D-xx`。

**结论**：**一条信息只有一个权威位置**——规则明细→spec、定位→SKILL.md、回写规则→drawio-loop、
决策历史→本文档，代码里只留一句指针。判据：**删掉它，下一个 AI 会不会做出错误的"改进"？** 会 → 留。

**结果**：两轮瘦身（删重复 + 压模块 docstring）891 → 506 行，18.8% → 14.2%。
**到此为止**——再压就得删 why-not 注释，是拿"下个会话改坏代码"的风险换几行 token。

**影响**：全部脚本；`verify/README.md` 的注释约定；`verify/contract.py` 的注释预算断言。

## D-11 产物审核：门禁都只查中间产物，没人看渲染结果

**曾这么定**：结构校验查《流程表》、质量门禁查 `flow.yaml`——**两者都不看渲染产物**。

**为什么改**：实测过——从 `flow.html` 删掉一个节点，`validate.py` 照样报「✓ 全部通过」。
渲染器少画一个节点，在原来的体系里永远发现不了。

**结论**：自检产出渲染契约（节点 id 清单 + 边清单 + 计数 + DSL 指纹），渲染后从两份产物**反解**结构
逐项比对，不符就阻断。**多个契约文件**按 DSL 名派生——否则 `sync` 的临时 DSL 会覆盖主契约。
比对用多重集而非集合，否则"把一条边画错目标"只会报"少一条"、不报"多一条"。

**影响**：`scripts/manifest.py`；`build.py` 第六环。

## D-12 同步的差异复核：从"集合比较"改成"文件级比对"

**曾这么定**：`--diff` 用集合比较（只看节点/边存不存在）就报"与流程表一致"。

**为什么改**：集合看不见分支顺序、编号后的自由注解、`回` 标记、换行符与 BOM。
而回写 diff 是 `--apply` 前**唯一要复核的界面**——一旦掺进"没动过的行也变了"的伪差异，这道复核就失效了。

**结论**：抽出 `writeback.compare_bytes()`，`sync` 与 `--diff` 共用（消掉两份实现），跑完结构 diff 再补字节级比对。

**影响**：`scripts/writeback.py`、`xml_reader.py`、`sync.py`。

## D-13 验收脚本会改写样例产物（曾把真信号当成抖动）

**曾这么定**：幂等检查拿 `examples/<样例>/flowtable.md` **就地**跑两遍 build，比较产物是否一致。

**为什么改**：它不复制到临时目录，所以 `examples/*/flow.html`、`flow.drawio` 会被**真的改写**。
后果是：渲染器一改，已提交的产物就过期 → 第一次 verify 必失败 → 跑完被就地改新 → 之后再跑全绿。
这个"自愈"把真信号伪装成了抖动（我最初就误判成抖动，查了四轮才定位）。

**结论**：不改行为（就地 build 有它的价值），但**改完渲染器必须显式重生成四个样例再跑 verify**。
这条写进 `verify/README.md`。

**后续**：本条结论已被两次后续决策取代——①"就地 build"被 D-20 推翻，幂等检查改在临时副本里跑
（`verify/README.md` 已按 D-20 口径重写）；②"四个样例"在 D-42 发布整理后只剩 `self-demo` 一个。
本条按当年口径读，现行口径以 D-20 / D-42 与 `verify/README.md` 为准。

## D-14 校验只查"行内自洽"，查不出"逻辑连不通"

**曾这么定**：H1–H7 只保证每一行写法对，漏填一个「下个节点」、写错目标编号、判断两分支指向同一处，
都能通过。渲染出来的是一张**看着完整、实际走不通**的图。

**为什么改**：这类缺陷用户看不出来，AI 也容易被"门禁全绿"误导。

**结论**：新增 H8 逻辑连通（孤立 / 孤儿 / 死胡同 / 不可达 / 结束可达 / 判断分支目标与标签重复）。
上线前先写原型扫四个真实样例确认**零误伤**，才设成阻断。

**影响**：`table_to_dsl.py` ③ 关系层；`references/flowtable-spec.md` 第 3 节。


## D-15 连线掉头折返：出边与入边共用同一侧锚点

**现象**（视觉审查实锤，4 个样例里 3 个都有）：入边与出边用同一侧、共用同一个锚点（该侧中点），
出边首段把入边末段**原路画回来** 110–150px——线压过节点边沿上的箭头，看起来像"线穿过了框"。

**为什么门禁没拦**：「边不重叠」豁免了共享端点的边。那条豁免只对**分叉/合流**成立（两条边同向汇到一点），
**掉头折返是反向的**，不是分叉——豁免写得太宽，把折返也放过了。

**结论**：`anchor()` 本来就支持偏移 `dy`，但源侧从没传过。新增 `sdye`（与目标侧 `dye` 对称）：
出边与入边用同一侧、且该侧中心被入边占住时，出边沿该侧挪开 2×细格，方向朝目标锚点那侧。

**三个实现教训**：上限别拍脑袋（`h/2 − 12` 而步长是 20 → 永远装不下，静默不生效）；时序要对
（端口是 `_ensure_gutters()` 才定的，挂 `__init__` 会拿默认端口判"同侧"，判错就静默跳过）；
`validate` 的 `paths` 是线段列表不是点列表。**影响**：两个 router 加 `_stagger_source_anchors` + `sdye`、
`render_drawio` 的 `exitY` 偏移、`validate` 第 5 项新增"掉头折返"判定。
**后续补漏**：原判据只覆盖"入边与出边同侧"，漏了**多条出边同侧**（16 的两条出边都从 bottom 出、首段共线叠成一条，害得 16→16a 的合法 Z 形被"重叠"罚掉）；现按侧分组依次让位。

## D-16 泳道行内多列的中线：余数必须与行高同余

**现象**：同一阶段行里，格内摞了 2 个节点的那一列，中线比只有 1 个节点的列差 10px——
横穿该行的连线于是从部门之间"错开半格"穿过，看着像没对齐。

**为什么**：节点四边守粗格（20）⇒ 摞顶落 20 格 ⇒ 栈中线必落在 `20k+10`。
单节点格的摞高 = 形状高（已是 `20 mod 40`），多节点格靠 `gap` 维持同余——**两者缺一，列间就差 10px**。

**结论**：`gap` 与 `row_h` 一律过 `_align_half()` 吸到 `20 + 40k`；摞顶 y 由**行中线反推**，
不做"顶边居中后吸格"（后者会把 570 吸成 580、整摞下移 10px，和别的列错开）。

**影响**：`scripts/swimlane.py`（`_align_half` / `_stack_top`）；`references/swimlane-spec.md` §3。

## D-17 泳道布线的三处修正：偏移语义 / 首段方向 / 被挡绕行

**现象**（视觉审查实锤）：① 并排节点的连线紧贴边沿，看着像穿过框；② 同行两节点中间隔着别的节点时
（泳道图 `19→20`），首段竖直折返、线压在 `19` 的右边沿上；③ 修 ② 时用 `dye` 错位锚点，把锚点推进了节点内部。

**为什么**：`anchor(nid, side, dy)` 把 `dy` 当 **y 方向**偏移，可上下边的端口边是水平的——按 y 挪必越界
（`y+h−20` 落进节点里）。而同行被挡时 `LaneRouter` 只试两条 L 形，都不通便无第三手。

**结论**：三处一起改。① `dy` → `off`，语义统一为**沿该边的切向**（左右边挪 y、上下边挪 x），
`geometry` / `swimlane` / `render_drawio` 三处解释同步；② 水平端口的首段必须水平（先竖直就贴在节点
边沿上，与同在边沿的入边末段叠成一条）；③ `_row_blocked()` 判"两条 L 形是否**都**走不通"，是才换
`bottom→bottom` 绕本行空带。它的判据必须是**实际折线**而非两端锚点连线——后者是斜的，会穿过没挡路的
节点，把干净直线误判成被挡（`03→04` 被误伤过）。

**影响**：`scripts/geometry.py`、`swimlane.py`、`render_drawio.py`、`lane_router.py`。

## D-18 `--no-layout` 会静默冲掉并排布局（重生成样例时踩过）

**现象**：改完渲染器、按 D-13 重生成四个样例，为图省事一律加了 `--no-layout`。结果 `self-demo`
的双列布局（`03b` 与 `03` 并排，`col_x: [400, 860]`）被压回单列，`verify` 的 gates 面当场失败
——那条"新增列却没补 col_x"的反例断言，就依赖样例里存在 `- 860`。

**为什么**：`--no-layout` 的语义是"**丢弃已有几何、按表序重排**"。而"哪两个节点并排"这个信息
**只存在于 `flow.yaml`**——流程表表达不了并列关系。所以它一丢就是永久损失，`auto_layout` 只会给单列。

**结论**：重生成样例一律用**默认模式**（`build.py <表>`，自动复用已有 `flow.yaml` 的几何）。
`--no-layout` 只在确实要重排时用，用完必须人工复核列归属。已写进 `verify/README.md` 与 `--help` 文案。

**影响**：`verify/README.md`（重生成步骤）；`scripts/build.py`（`--no-layout` 的 help 警示）。

**后续**：D-37 之后，"同汇聚点"型并排（self-demo 的 03/03b 正是）已可由流程表直接推导，`col_x` 现为空表
——判据内的形态不再依赖 yaml；判据外的并排仍只在 yaml，本条警告对它们仍然成立。

## D-19 切标题带必须作废 router/labeler 的矩形缓存（HTML 版放行过穿节点的直线）

**现象**：drawio 版里 `19→20` / `24→25` / `07→08` 都是绕开中间节点的折线，HTML 版同一条边却是
一条直挺挺横穿节点盒的直线；`validate` 报"零边穿节点"，与产物自相矛盾。

**为什么**：`render_html.py` 调 `L.head_band(False)` 把整张图 y 平移 `legend_h`，但 `Router` /
`LaneRouter` / `Labeler` 三处的节点矩形缓存（`_rects`）**在构造期就被填好了**（`LaneRouter.__init__`
→ `_stagger_source_anchors` → `ports` → `_row_blocked` 一路读矩形），切换后没人清它。于是避让判定
拿**新坐标的候选**去撞**旧坐标的矩形**——`18` 的新矩形 `y=1060`、缓存里却是 `y=1140`，直线"不命中"，
放行。drawio 版不受影响：它不切带，且走 `exitX/exitY` 端口参数 + drawio 自身正交布线。
（`validate` 查的是新坐标系，所以它说没事；两套坐标系各自自洽，只有产物是错的。）

**结论**：`Engine.head_band()` 里一并作废三类派生缓存（三个 `invalidate()` + `_width`）。
凡是"从 grid 派生并缓存"的东西，栅格几何一变就必须清——缓存不是纯优化时，就不该只有懒加载。

**影响**：`scripts/engine.py`、`routers` 与 `label.py` 各加 `invalidate()`；`references/visual-spec.md`。

## D-20 验证不得污染工作产物；build 覆盖前先留存

**现象**：verify 的「幂等」项直接对 `examples/<样例>/` 跑 `build.py`，把用户在 drawio 里的手工微调
**静默覆盖**了；而"幂等"这条断言本身也因此误报失败（它拿被手改过的产物当基准）。

**为什么**：`build` 的契约就是"从《流程表》重新生成一切"——覆盖是设计行为，不是 bug。矛盾出在
验证层把"工作产物"当成了"可随意重写的临时件"，而这两类文件恰恰放在同一个目录里。

**结论**：① 幂等检查一律在临时副本里跑（复制 `flowtable.md`/`flow.yaml`/产物到 tmp 再 build），
并补一条"验证过程未改 examples/"的断言；② `build.py` 渲染前把旧产物读进内存，若渲染结果不同则
留一份 `.flow.<ext>.bak`——手改被覆盖后还有得救。**用户的 drawio 改动要走 `sync.py` 回写《流程表》，
不要靠重跑 build 生效**（这条也写进 `SKILL.md`）。

**影响**：`verify/invariants.py`、`scripts/build.py`、`SKILL.md`、`verify/README.md`。

## D-21 新增「终端子流程」类型：有入口、无出口的旁支终点

**现象**：转录白板时出现 3 个节点（各类「结算子流程」「签订子流程」），业务上由某个进件的条件分支进入、
办完即止、**不回主干**。填成「任务」→ H8 报死胡同；填成「结束」→ 图上多出三个椭圆，而 `结束` 是
"全流程唯一终点"的语义，H1/H8 判定立刻变成歧义。

**为什么**：原类型表只承认两种"没有出边"的节点——`结束`（全局终点）与（错误写法下的）死胡同。
"局部旁支的终点"是**第三类**：可以有多个、主干不在此收束。是类型表缺了一格，不是表填错了。

**结论**：新增 `终端子流程`（DSL `subflow_end`）：出边「不许有」，与 `结束` **共用 H5 规则**（H 编号是
规则主题、不是类型清单，故不为它单开一个；报错文案改按 `rule['cn']` 取名，否则这条 H5 会硬说自己是
"结束节点"）；「下个节点」填 `—`，且**必须有入边**（否则是孤儿，H8 照报）；视觉 = `shapes.subflow_end.dashed`
（虚线圆角矩形）。中文名映射 3 处（`TYPE_MAP` / `DICT_ZH` / `TYPE_ZH`），漏改任一处 drawio 往返就会读丢类型。

**影响**：`table_to_dsl.py`、`dictionary.yaml`、两个 renderer、`xml_reader.py`、`writeback.py`、
`flowtable-spec.md`、模板、`SKILL.md`。

## D-22 「泳道列序」显式声明 → 列序不再由首次出现决定，并同时开启槽位模式

**曾这么定**：列序 = 执行主体的首次出现顺序，想调列序就改流程表的行序。

**为什么改**：① 白板/协议往往已画定部门左右次序，让"谁先被表提到"决定列序 = 把转录顺序当业务约定；
② 全空泳道（某部门本流程不参与）没有节点去认领它，首现顺序下根本画不出来。

**结论**：元信息支持 `- 泳道列序：A → B → C`，照单全收（含空泳道）。列名须与「执行主体」一字不差，
否则凭空多一列空泳道。它同时是**槽位模式的开关**——两者不能分开定，因为槽位求解的输入就是列序（见 D-23）。

**列序怎么定**：把列序当自变量，`Φ(列序)` = 同阶段逆行边数，求 Φ 最小（≤8 条泳道直接穷举）；
`K = 阶段数 + Φ` 即槽位数。Φ 有**结构下界**（同泳道先后边 + 跨泳道业务回退，二者都消不掉），
所以"最小 K"可当验收基准——实测：白板序 Φ=8/K=14，交换两条泳道后 Φ=7/K=13。
**注意**：最小 K ≠ 业务最优（K 少 = 更多节点压进同一行）；自动求解只作建议，定稿由人写进「泳道列序」。

**影响**：`table_to_dsl.py`（`parse_lane_order` / `subject_map` / `apply_swimlane`）、`swimlane-spec.md` §2.1。

## D-23 泳道行轴：`stage` → 「流程槽位」，等距层高

**现象**：一个阶段常含多个先后步骤（"备货"下有申请/审核/发货/签收/启动）。一行 = 一个阶段时这些节点
只能在同一格**纵向摞成一摞**：行高被撑大，而其他列只有一个节点、按行中线居中 → 悬在两条行线正中
（实测其他泳道 16 个节点里 11 个的中心 y 落不到行线上）。

**为什么**：不是参数没调好，是**粒度错了**——阶段是业务分组、槽位是几何层，当同一个东西用就必然堆叠。
用户手改版反推也印证这点：它实际有 14 条水平槽位，而非 6 行。

**结论**：声明「泳道列序」时 `row` 从阶段号细化为**槽位号**，层高严格等距 `lane.pitch`。用
`slot(v) = max over 入边 slot(u) + (0 if stage 相同 且 col(v) > col(u) else 1)`——`max` 而非顺序
递推，天然处理分支/汇聚；空槽号压缩掉，含回路时退回表序并留提示（不静默）。左轴阶段带改按
`lanes()['stage_spans']`（连续同阶段行区间）合并绘制，网格余数与兼容路径见 `swimlane-spec` §3.1。

**影响**：`swimlane.py`、`table_to_dsl.py`（`_topo_order` / `assign_slots`）、两个 renderer、
`dictionary.yaml`（`lane.pitch`）、`swimlane-spec.md` §3.1。

## D-24 H6 死循环检测：剪枝子图判环，替代逐起点 DFS + 全局剪枝

**现象**：纯任务回路 03→04→05→06→回03 与判断捷径 04→07(判断)→05 并存时，H6 不报、照常渲染。

**为什么改**：旧算法用全局 `seen_edges` 剪枝省时间，但"边探过了"≠"环判完了"——捷径先把 04→05 段
消耗掉，别的起点再探时纯任务回路断在剪枝上。规则承诺"每个回路至少一个判断"，检测器却在
"还剩没有判断的环吗"这件事上失真。gates 只测过最简两节点回路，测不出这类。

**结论**：等价改写——删掉所有判断节点及其邻接边，剩余子图**不得含有向回路**（含判断的环本就不该报）；
子图上跑三色 DFS，GRAY 返祖边即环，节点集 frozenset 去重。O(V+E)，没有跨起点共享的剪枝状态可污染。

**影响**：`table_to_dsl.py`（`check_deadloop` 重写）；verify 面②补并联捷径回归用例。

## D-25 回写只重建表格本身：表格之后的内容必须原样保留

**现象**：流程表按模板带「## 列填写规范」整节，一次 `--apply` 后整节消失——旧回写只拼
"表头前前言 + 新表"。且表头行不含「节点编号」时 head 取整个原文，输出 = 全文 + 新表、节点全量重复。

**为什么改**：回写的契约是"更新这张表"，不是"重写这份文档"；表格只是 markdown 文件的一部分，
diff 预览看的是整份文件。

**结论**：表格块 = 含「节点编号」的表头起**连续** `|` 行；块后内容逐字拼回（无散行时保持逐字节一致，
`sync` 的复核界面才可信）。中段被空行隔开的散表行按 id 剥除（body 已重建全部节点，保留会出现两行）；
单元格里的 `|` 落盘转义为 `\|`（GFM）。缺标准表头直接报错退出，不硬猜。

**影响**：`writeback.py`、`semantics.py`（`split_table_row`）；verify e2e 补表后内容保留断言。

## D-26 `--layout` 提示从「只借几何键」放宽为「几何键 + 手调 kind」

**曾这么定**：`reuse_hint` 以 (from, to, kind) 三元组查提示表，kind 一律由几何重推导——手改 kind 后
三元组失配，kind 被静默重置，该边 gutter/channel/dye 也连带丢失（dsl-spec §4 却声称 kind 可手调）。

**为什么改**：提示 yaml 本身就是手调成果的载体（build 默认复用 flow.yaml），"手填值被静默重置"
违背 D-15 确立的原则。未手调时提示 kind 与几何推导值相同，按提示取并无副作用。

**结论**：按 (from, to) 匹配（label 优先、kind 次之、逐条消耗，兼容并联出口），命中则 kind 从提示、
loop 自动 negative；几何键清单补全 `gapx`/`sdye`。label / polarity 仍以流程表为准。

**影响**：`table_to_dsl.py`（`reuse_hint`）；`dsl-spec.md` §3/§4、SKILL.md 措辞同步。

## D-27 泳道对向端口走 Z 形：L 形必有一端贴边

**现象**：项目启动→施工、并网进件→运维介入等边是 L 拐——水平段**贴着目标节点上边框**，
箭头横着顶进顶口。几何门禁查不出：`_hits` 豁免源/目标自身，validate 横穿检查内缩 6px 也放行贴边线。

**为什么改**：D-17 立过"首段方向必须 = 端口法线方向"，但**末段没执行同一条原则**——bottom→top 且
两轴都有偏移时，两条 L 候选各有一端违规（to_v 末段水平滑进 top 口、to_h 首段水平离开 bottom 口）。
候选清单里根本没有两端都合法的 Z 形，违规者自然中选。

**结论**：`LaneRouter.path` 新增 Z 候选（中段在两锚点开区间内折一次，中点吸细格，撞节点向两侧
交替偏移重试），仅对**对向端口**（下→上 / 上→下 / 左→右 / 右→左）且两轴都有偏移时启用、
排在 L 之前；同侧组合（bottom→bottom 行内绕行）仍走空带候选。开区间保证首末段不反向。

**影响**：`lane_router.py`（`_z_cands`）；`swimlane-spec.md` §4；pv-swimlane 产物重渲染（7 边变化：
3 个贴边 L 改 Z，4 个空带 Z 换中点 Z）。

## D-28 流程布线三则：前向对角走 L、回路错峰内圈优先、右通道局部基准

**现象**（self-demo 三条反馈）：① 相邻列的边一律走列间空隙（左右端口），03b 的进出全挤在左口，L 根本不在候选里；
② 回路错峰按边表顺序发槽位，08→03（外道）的入场横段恰好穿过 04→03（内道）的竖段；
③ 08→09 的右通道落在 1000——基准是全图最右列中心（860）+140，而这条边两端都在 c0（右沿 480）。

**结论**：① 前向对角（下行跨列）先走干净 L（右下=右出顶入、左下=底出右入；折点记 `gapx`、端口记 `exit`/`entry`），
带锚点占用守卫——目标/源端口已被其他边占用（显式或按 kind 默认）就跳过：叠锚点的重叠段会被 validate 的共享端点豁免放行。
② 回路错峰**内圈优先**：近源先拿靠源一侧的槽位、远源向对侧让位——外圈横段从内圈竖段上方绕过，零交叉、外圈包内圈嵌套。
③ 右通道**局部基准**=本边涉及列中更靠右列中心+`right_channel_offset`；废除"右族须在全图最右节点右沿之外"的
分侧教条（左族保留——左族越界必穿节点），撞更右列节点由逐候选检查拦下。

**泳道不动**：D-27 的 Z 是用户点名要的，且泳道列是部门语义、顶入保留"下一槽位在下方"的读法。

**影响**：`router.py`（`_candidates`/`_stagger_target_dyes`/`_ensure_gutters`/`_anchor_taken`/`path` 去重）；
`visual-spec.md` §2/§3、`dsl-spec.md` §3、SKILL.md 第 4 环；self-demo 重渲染（恰 5 边），其余示例不变。

## D-29 新列插入点：`col_pitch` 460 从硬编码提为声明参数

**现象**（用户指出的薄弱项）：dsl-spec 只说"新增列要同步补 col_x"，没说**补多少**——460 的事实标准

（visual-spec §6 指引），每拆一列都要猜一次插入点，填窄了要等门禁报通道冲突才知道错。

**结论**：列间距声明为 `layout.col_pitch`（默认 460 = 节点宽 160 + 列间通道带 300——通道带要容下
`col_gap_step` 交替展开与 D-28 右族局部基准，压到 300 以下会挤爆）。新列中心 = 上一列中心 + col_pitch
（400 → 860 → 1320…）；未声明 col_x 的多列 yaml 按此展开（geometry 回退读字典）；xml_reader 的
无几何回退同口径。写入 dsl-spec §4（手调指引的家）与 visual-spec §3 参数表。

**影响**：`dictionary.yaml`、`geometry.py`、`xml_reader.py`（注释）、`dsl-spec.md` §4、
`visual-spec.md` §3/§6；默认值不变，产物零变化。

## D-30 泳道布线择优：形状合法 → 交叉最少 → 折点最少

**现象**（用户手改 43 节点泳道图，逐边对照后归纳）：原实现"第一个不穿节点的候选就返回"，看不见别的线。
用户的选择反复落在"与已有线条交叉更少"的那条上；长回环（36→01 跨 30 槽）被推到画布最左缘 x=40、
次长的（01b→20）依次内收，原实现方向恰好相反（`gutter_inner=280` 起越退越靠内）。另有 9 条边带 10px 残段。

**结论**：① 候选择优排序改为 **形状合法（端点段沿端口法线）→ 与已有线条交叉最少 → 折点最少**。
形状必须排第一：实测 pv-swimlane 的 15→16 会因"折点少"选中贴边 L，把 D-27 的正确 Z 挤掉。
② 交叉数需要**全图信息**（路由长边时短边未定案，各候选的交叉数都是 0），故：跨度降序贪心出初始解，
再做**坐标下降**——每次只重选一条边、其余固定，仅接受代价严格下降的改动。全图代价单调递减 ⇒
必然终止、结构上不可能震荡（早先"每轮全体重选"会 A→B→A 来回）。代价 = 重叠 ≫ 形状非法 ≫ 交叉 ≫ 折点。
③ 回环与同列长跳都增加"画布外缘分层通道"候选（`_far_cands`）+ 贴列沿候选（`_side_cands`）。
④ 锚点切向差 ≤1 细格视为对齐，消除残段。

**影响**：`lane_router.py`（`_pre_route` 贪心+坐标下降 / `_cost` 代价 / `_bad_ends` / `_far_cands` / `_side_cands`）、
`geometry.py`（`ortho_cross`）；四示例逐字节零回归，泳道 43 节点图八项门禁由 16 项冲突降至 0。

## D-31 非矩形节点的端点按真实形状判：菱形内接，外接矩形边不是边界

**现象**（用户"箭头没搭到框上"，实测确认）：泳道图 6 处端点悬空 8.9~27.5px，全在菱形节点上（`12→13` 16.1px、`13→10` 27.5px）。菱形**内接**于外接矩形，只有边中点与矩形重合；锚点沿边错峰或用"微折点对齐"挪 10px，线就离开斜边悬在空中。

**为什么门禁没拦**：全项目约定"形状即格位，布局器/布线器/校验器只认外接矩形"——校验器也只比矩形，而菱形在该处的真实边界比矩形边**内收**最多半宽，于是"悬空"和"贴住"在矩形判据下长得一样。

**结论**：① 布线层：`anchor()` 对非矩形节点把切向错位**投影回真实边界**（菱形 |dx|/hw+|dy|/hh=1、椭圆 (dx/hw)²+(dy/hh)²=1），投影后吸细格——偏移本身不禁止；但**孤立偏移直接归零**：某端口只剩它一条边时，
错峰已失去理由（本是为让位，竞争者被挪走后只剩"把锚点推上斜边"这一个后果），布线程在端口定案后复查、清掉自己设过的那批（`sdye` 手填的不动），再冻结端口干净重解一趟；同侧挤多条出边时先把多余那条挪到空着的垂直侧。
渲染器的端口比例改由 `anchor()` 反算（`port_frac`），不各算一份。
② 微折点对齐改写成 `dye`（而不是在候选里直接改写坐标）：渲染器读的是 `dye`，绕过它就会画出与折线不符的起点。
③ 门禁端点评据升级为**按形状**判（`_on_border(p, rect, shape)` 用 `r·(1 − 1/t)` 算点到内接曲线距离）；"横穿自身节点"同样按形状判
（投影后的锚点本就在外接矩形内部，按矩形判会误报）。④ gates 加谓词回归用例。

**影响**：`geometry.py`（`anchor` 投影 / `port_frac`）、`swimlane.py`（`port_frac` 别名）、`lane_router.py`（`_align_anchors` 写 dye / `_spread_contended_ports` 挪端口 / `_drop_orphan_offsets` 清孤立偏移）、
`render_drawio.py`（端口比例同源）、`validate.py`（`_on_border` / `_seg_in_shape`）；五张图悬空全部归零，四示例产物重生成。

## D-32 门禁读产物：几何表的复核只认产物里的真实坐标

**缺口**（用户："我看到很多节点缕空"，并提议"生成节点/连线的坐标表单，由脚本门禁自检"）：`validate.py`
读 `flow.yaml` 并用 `L.path(e)` **现算**折线——与渲染器**共用同一个 router**。router 把线接歪，模型门禁
与产物一起错、一起"通过"；第 6 环契约反查只比"有哪些节点/哪些边"的**集合**，一个坐标都不看。

**结论**：① 新增**几何表** `artifact_geometry()`：drawio 取 `mxGeometry` + `Array as="points"` 折点 +
`exit/entry` 比例反算端点；html 取 `.ndg` 的 `translate` 与形状元素、边的 `d`。**形状也从产物读**，
不按类型回查字典——回查就又同源了。② `check_artifact()` 对这份几何跑六项（重叠/穿节点/端点接框/
边重叠/画布/网格）：判据复用同一批检查函数，只用 `_ArtifactL` 把数据源换成产物；产物里没有标签盒，
第 6 项（标签）不在产物侧做。③ CLI `validate.py --artifact <产物> [--dump geom.json]`；`build.py` 在
契约反查后内置这一关（html + drawio 各一次），不过则 exit 1。

**影响**：`xml_reader.py`（`shape` / `pts` / `exit` / `entry` / `page` + `geometry()`）、`manifest.py`
（`geometry_from_html` / `artifact_geometry`）、`validate.py`（产物复核层 + CLI）、`build.py`（末环）、
`gates.py`；五张图 × 两产物全过，且"把端口比例改歪"能被产物侧报出而模型门禁仍全绿。

## D-33 泳道摞顶按格内最严的形状定刻度：纯菱形格不再被推下 10px

**现象**（重渲染 `output/` 时暴露）：泳道槽位模式下 9 个只放了一个「判断」菱形的格子，整体比同行矩形格低 10px。
根因：行中线恒为 `20k+10`，而 `160×80` 菱形 `摞高/2 = 40 ≡ 0 (mod 20)` ⇒ 摞顶 = 中线 − 40 必落在 `20k+10`；
`_stack_top()` 却一律 `snap(top, 20)`，于是把整摞推下 10px。同一处还刷屏：它在**取值路径**（`rect()`）里追加提示，
`rect()` 每调一次就重记一条——36 条提示里只有 10 条不同。

**结论**：① 摞顶的吸附刻度按**该格最严的形状**定：含矩形类节点 → 粗格 20；整格非矩形 → 细格 10
（visual-spec §0 本就只要求非矩形守细格）。② 摞顶改在 `_build_rows()` 里一次预算（`_stack_y`），
`rect()` 变成纯取值、无副作用；提示随之一格一条，措辞也去掉问号改成断言。

**影响**：`swimlane.py`（`_snap_unit` / `_build_rows` / `rect`）、`swimlane-spec.md` §3、`gates.py`；
`output/泳道实验图` 9 个菱形格上移 10px 回到行中线，`examples/pv-swimlane` 逐字节未变。

## D-34 错峰符号平局时按行进方向定向：一去一回各占走廊一侧

**现象**（写 D-33 的回归用例时撞出来的既有缺陷）：泳道同行的一对反向平行边 `02→01` 与 `01→02`
布不通，八项门禁报「边 02→01 横穿自身节点 02」。查候选代价：9 个形状合法的 Z 形**全部**被
`W_OVERLAP` 罚到 `10⁹`，只能退化成两端都不沿端口法线的坏形状（代价 2×10⁶ 反而最低）。

**根因**：`stagger_source_anchors` 的符号取"切向朝目标锚点"（`1 if ty >= sy else -1`）。同一行的两个
节点锚点等高 ⇒ `ty == sy` 恒成立 ⇒ **平局一律取 +1**。两条反向平行边各自独立算符号，于是都取 `+20`，
两条出线段落在同一 y 上必然共线重叠。

**结论**：平局时改按**行进方向**定向——左右端口看目标的 x 在源之左还是之右（`tx > sx` 取 +），
上下端口看目标的 y 在上还是在下。一去一回方向相反 ⇒ 符号相反 ⇒ 各占走廊一侧，形状合法的候选
不再与对方重叠，代价函数自然选回正确的 Z。（非平局时仍用"朝目标锚点"，行为不变。）

**影响**：`geometry.py`（`stagger_source_anchors`）、`dsl-spec.md` 的 `sdye` 行、`gates.py`；
五张图两产物**逐字节未变**（只在"同行反向平行边"这一配置上生效），复现用例八项门禁全过。

## D-36 向右交棒要跨过同槽节点时另开一槽

**现象**（用户按诊断图指认）：泳道图 `17→18` 贴着 17/18 的边框走（20px）且与边26 交叉，`18→19` 也被挤成 Z 字。
根因在**布局**不在布线：槽位规则"同阶段向右交棒 → 同槽"让 17(col0) 与 18(col2) 同槽，而这个槽里还站着 16a(col1)

**结论**：同槽条件再加一条"**中间没人**"——向右交棒时，若同槽里已站着夹在两列之间的节点，就另开一槽。

**影响**：`table_to_dsl.py`（`assign_slots`）、`swimlane-spec.md` §3.1、`gates.py`；四个示例的行列**零变化**
（只有泳道实验图重排：多一层，画布高 4030 → 4150）。

## D-37 并行分支并排：汇聚到同一点的分支自动占相邻列

**现象**（用户追问"泛化性"时实测）：`self-demo` 是唯一带"并排"关系的样例——判断 `02` 的两条分支 `03`/`03b`
并排。但那是**手调**留在 flow.yaml 里的那一列：`auto_layout` 的基线是"表序 × 单列"，列从来不是算法量。
所以从表重跑会把 `03b` 排到下一行，`02→03b` 就得绕过 `03`，多出 1 处交叉 + 2 个折点。

**结论**：新增 `merge_parallel_branches()`，只挂流程布局的**基线路径**（泳道与 `--layout` 复用不走）。
判据保守——分支节点的**后继集合完全相同且非空**（"判断走 A 还是 B、两条都汇到同一点"）才并入同一行、
占相邻列，并把腾空的层压掉；后继不同的普通分叉一律不动。多列时 `col_x` 写**空表**、由字典
`layout.col_pitch` 展开（不在脚本里再抄一份 460）；空表与"没写这个键"在复用路径里必须分清。

**影响**：`table_to_dsl.py`（`merge_parallel_branches` / 基线 `col_x` / 提示路径的空表）、`gates.py`；
`self-demo` 由 12 折点 1 交叉降到 **10 折点 0 交叉**、少一层空行；另三个样例行列**零变化**。

## D-38 左侧里程碑带不许走线：列外走廊按需预留

**现象**（用户按 `flow.html` 指认）：泳道底图最左边那条里程碑带被 4 条回环的竖段穿过（x=40/80/120，带宽 120）。
根因：左族远通道从画布左缘起算（`margin=40`），而带子左边那块空地在布局里**根本没被声明为"不可走"**
——它最好走，于是长回环全挤了进去，视觉上就是"底图与线撞车"。

**结论**：① 左族从**带右沿**起算（流程布局没有带 → 仍是 0），压带在结构上不可能；② 带外走廊**按需预留**：
**同列跨行的长跳**必须绕开本列的中间节点，每条要一条列外竖通道，宽度 = 条数 × `gutter_step`
（字典 `lane.route_left` 可抬下限）。只留一条通道时那 4 条长跳会挤进列缝，交叉由 1 涨到 7——所以是"预留"
不是"回填"。

**影响**：`swimlane.py`（`route_left`）、`lane_router.py`（左族基准）、`dictionary.yaml`、`swimlane-spec.md` §5、
`gates.py`；泳道图交叉 1 → **0**、穿带 4 条 → **0**、画布宽 960 → 1160；`pv-swimlane`（无同列跨行长跳）
走廊 0、**逐字节未变**。

## D-39 左走廊宽度：从"估算"改成"测量"，并把"压带"做成产物侧门禁

**背景**（用户："既然是估算的，要不要将其规范化明确下来？"）：D-38 的走廊宽度是**估**出来的
（同列跨行长跳的条数 × 间距）。估小会让长跳退回列缝、交叉变多；而"不压带"只靠一句口头保证。

**结论**：① 宽度改成**探布量出**——引擎先按旧口径（左族从画布左缘起算）布一趟，数出真落进带里的边
有几条，按条数把走廊留到带右边，再**干净重解**定案（`LaneRouter.explore` + `Engine._reserve_left_corridor`）。
顺路一步就到的回路由更便宜的走法接走，探布时压根不进带，所以不会把走廊撑大。
② "压带"升级成**产物侧门禁**：`check_artifact` 从产物读出里程碑带宽（底色带一律从 x=0 起画），
任何折点落进带内即报错——带宽不靠配置反推，渲染器少画/多画一条带也躲不过（接 D-32 的思路）。

**影响**：`engine.py`（两趟）、`lane_router.py`（`explore` / `release`）、`swimlane.py`、
`xml_reader.py` / `manifest.py`（读带宽）、`validate.py`（带内判据）、`gates.py`；
泳道图走廊 200 → **120**（量出来的更准）、画布宽 1160 → 1080、交叉仍为 0；`pv-swimlane` 走廊 0、未变。

## D-40 每一段不短于一格粗格：微残段的成因与硬约束

**现象**（用户按 `flow.html` 指认）：`泳道实验图` 第 9 号边（`06→10`）是 C 形，两端平行的
水平段各只有 **10px**——比箭头（约 9px）长一点点，转角基本压在箭头上。

**成因**：不是漏算，是**代价函数里压根没有"腿长"这一项**。该边走贴列沿通道，`_side_cands` 的内缩量是
`HIT_MARGIN + 细格 = 14`（吸附后 10px）；它最内缩，折点数与交叉数又与其他候选持平，排在最前就赢。

**结论**：① 贴列沿通道的内缩量改成**一格粗格**（`HIT_MARGIN + 2×细格`）；② `_cands` 加硬约束 `_legs_ok`
（每段 ≥ 20px），与"不穿节点"并列——两者都满足的没有时退一步只保证"不穿节点"，不能为腿长逼出穿节点的线；
③ 升级为**产物侧门禁**：`check_artifact` 逐段量长，短于一格粗格即报"转角挤在箭头上"。

**影响**：`lane_router.py`、`validate.py`、`gates.py`；`06→10` 两端 10px → **20px**；五张图"段 < 20px"
全部归零，折点/交叉一个没变；流程布线器未改（产物侧门禁同样管着它，实测三张流程图为 0）。

## D-42 发布整理：样例只留自举，用例改自带合成表

**结论**：① 清单固化进代码 `validate.ARTIFACT_RULES`（九项 = 六项与模型侧同义 + 微残段 + 泳道两条），
contract 逐名核 `visual-spec` 与 `SKILL.md` 两处都写到，并核「不查什么 / 标签盒不在产物 / 还原」三处边界；
② `visual-spec` §4.1 改成契约块（查什么表 / 不查什么 / 怎么消费），`--dump` 补齐泳道带宽与底色盒、
以及 `exit`/`entry` 端口比例（起点终点就是它反算的，摆一起才看得出为什么接歪）；
③ `build.py` 审不过**还原**产物、明说"不留没审过的交付物"，`.bak` 改到审过之后才写（旧版没变就不用留）。

**影响**：`validate.py`、`build.py`、`xml_reader.py`、`SKILL.md`、`visual-spec.md` §4.1、
`templates/checklist-template.md`、`contract.py`、`gates.py`。

## D-45 「下个节点」列纳入语义兜底：冲突时拦截，不静默取图

**曾这么定**：D-01 的"语义列以原流程表为准"只实现在 `writeback` 的 `default` 表上，覆盖 stage/desc/subject/executor/time 五列。
`下个节点` 不在其中——`nxt` 在 `build_rows` 里由 drawio 的边**全局重建**，原表的 next 只用来取措辞，不参与"该走哪条边"的判断。

**为什么改**（用户审查："怀疑 drawio 生成后再与交互修改环节，不会将改动同步与流程表核对，会导致变更后的流程被覆盖"）：
**成立**，P0 级。流程表把 `04 不通过→回 05` 改对 → 忘重跑 build → 用户拖几何触发 sync → `--apply` 静默改回
`回 03`，**EXIT 0、H1–H8 全过、八项门禁全过**：四道护栏校验的都是"回写结果"自身自洽性，从不校验它相对流程表丢了什么。

**结论**：该列的值**就是**图里那条边的目标，重建是必然的，没有"取原表就不看图"的选项，兜底只能是**冲突报警**：
① `writeback.branch_conflicts()` 按 `(label)` 配对比较目标集，只报方向性冲突（纯增删算正常操作）；
② `write()` 打印冲突警示（节点号 + 标签 + 两侧目标）；③ `sync.py --apply` 覆盖前拦截（退出码 1，表不动），
`--force` 才覆盖；④ `diff()` 的边差异改成两栏方向标注，不再写成"新增/删除出边"（那句话把因果讲反了）。

**影响**：`writeback.py`、`sync.py`、`xml_reader.py`、`SKILL.md`、`drawio-loop.md`、`gates.py`、`contract.py`。

## D-46 `⚠` 拆成两类、给「推不出的推断」一个收敛条件（不违反 D-02）

**曾这么定**：`⚠` 只有一个标记，兼表"AI 有依据的推断"与"AI 推不出、须业务方拍板的决策"。
**为什么改**：这意味着 `⚠` **没有收敛条件**——两种都能永远留在图上随图交付，用户分不清哪几处要自己拍板。

**结论**：`⚠`（有依据的推断，不必问）与 `⚠?`（推不出、必须问）并存；判据 = AI 独自找不到依据 **且** 不同选法后果不同（合规/成本/责任）。
① `semantics.pending_kind()` 分拣，`is_pending()` **语义不变**（任何 `⚠` 前缀都算，`⚠?` 照样画虚线）；
② 新增 `scripts/clarify.py` 算 frontier = {`?` 节点 n | n 的前驱无一标 `?`}，**不进 build 六环**（是问之前的准备，不是渲染的一环）；
③ 环里退化为按表序取首个破环并在 `blocked` 说明，不静默卡死。

**与 D-02 的关系**：D-02 否决"人审卡点"，两条理由是①拦不住糊弄 ②要用户读流程表。
本设计都不触碰：**不让 AI 自声明已确认**、**用户一个字都不用读表**、交付时如实报「仍未决 N 处」。
D-02 否决的是"让用户审流程表"，这里加的是"让 AI 问出缺口"——方向相反。**D-02 仍然有效，不得据此条重提否决。**

**影响**：`semantics.py`、`clarify.py`（新）、`flowtable-spec.md` §2、`SKILL.md`、`checklist-template.md`、`gates.py`。

## D-47 子流程下钻：`⊞` 声明 + 跑马灯环 + 多页，一份流程表一层

**背景**（用户："给节点做一个点击动作……链接跳转到新 html 页面来展示它的流程。类似于流程的嵌套。"）：
主图 13 节点 1180×1490 又细又长，根因是**一张图扛了两个层级**——骨架（谁保证这一步）与实现（调哪个脚本、读哪份规范）。
下钻 = 把实现层移出主图、按需展开。

**结论**：① 声明写在「节点描述」里（`⊞ parts/渲染.md`），不新增第 10 列——描述列已有 `★`/`⚠`/`⚠?` 三类标记；
② 下钻页的**事实源是独立流程表**（不是静态 HTML 片段），所以它仍可 `--check`/`build`/`sync`/再下钻，真正无限层级；
③ 视觉上用**跑马灯环**（节点形状等距外扩 4px 的流动虚线）而非描边或角标：描边已被 `⚠` 占用，环用**运动**这个新通道
（时间维度），不抢静态通道；早期右上角 `⊞` 角标是静态的，说不出"内部还有东西在跑"，且挤在小节点角上会糊；
④ 子表产物名按 D-51 **带子表自己的流程名**（`⊞ parts/渲染.md` → `parts/渲染-flow.yaml`），
**不是**约定的 `parts/flow.yaml`、也不是按后缀猜的 `parts/渲染.yaml`；
⑤ 下钻入口 `data-sub`：HTML 侧**切视图**（单文件，见 D-52），drawio 侧走同文件子页 `data:pageId`，**无 `⊞` 时逐字节不变**；
⑥ drawio **只铺一跳**（本图 + 直接子图），下一层交给子图自己的文件——递归平铺会让同一张子表存在于两个 `.drawio` 里。

**影响**：`semantics.py`（`subflow_ref`/`subflow_target`）、`render_html.py`、`render_drawio.py`、`build.py`、`manifest.py`、`flowtable-spec.md` §2、`visual-spec.md` §1、`gates.py`。

## D-48 下钻的回程：返回主图时恢复视窗位置

**背景**（用户："返回之后，为什么我此前的窗口视图跳回去了？……这会导致我失去焦点，忘记了我之前看到哪里了。"）：D-47 把"实现层"移出主图，让主图变短——但**大图仍然是大的**（自举图 1490px 高，仍需滚动）。
浏览器默认在同页面内记住滚动、跨导航则重置，于是"点进去看懂了，回来从头开始"。

**结论**：① 每个产出的 HTML 都自己记忆视窗位置（`window.scrollX/Y` + `.chart-container` 的 `scrollLeft/Top`），
存 `sessionStorage`、**按 `location.pathname` 分键**（同一次会话里主图与三张子图各记各的，互不覆盖）；
② 恢复**必须在 `fitHead()` 之后**——布局还没定时滚会滚到错的位置，白恢复一次；
③ 用 `scroll` 事件**节流 200ms** 保存 + `beforeunload` 兜底，否则快速跳转会丢掉最后一段位移；
④ 只记位置，**不记悬浮/缩放/选中**——那是"阅读状态"，恢复它反而像被接管，位置才是"我读到哪儿了"。

**为什么不是"回到顶部"或"滚到被点的那个节点"**：前者等于没记；后者把"我刚才在对比右下角那块"篡改成"你点了这儿"——用户要的是自己停下来的地方，记位置是唯一不替用户做决定的做法。

**后续**：D-52 单文件化后 `pathname` 不再区分层级，键已改为 `pathname#视图key`（见 D-52③）——本条"按 pathname 分键"是单文件之前的口径；2026-09-13 修的 SCROLL_KEY 初始键缺陷正源于这一次口径切换。

**影响**：`render_html.py`（`SCROLL_KEY` / `restoreScroll`）、`visual-spec.md` §1、`flowtable-spec.md` §2、`gates.py`。

## D-49 颜色是体系：流程表声明名字，跨层继承，冲突阻断

**背景**（用户："要做的是一个体系，而不是局限在这个 SKILL……**怎么设定颜色不重要，重要的是一致性**。
这个一致性最好要给脚本来进行检查和验证。"）：配色原按**各表首次出现顺序**分配，于是主图「机器」排第 3 拿到橙、
子图只有「机器」一个主体拿到蓝——点橙色的节点进去看到一整页蓝色。同一个执行主体跨层两个颜色，
不是"不好看"，是**同一个身份有两张脸**。

**结论**：① 声明写在**元信息区**（`- 执行主体配色：用户=蓝 ｜ AI=绿 ｜ 机器=橙 ｜ 双方=黄`），
声明**颜色的名字**（`蓝/绿/橙/黄/紫/红/灰`）而非十六进制——名字是**可判等的值**，脚本才查得了一致性；
② **子表不声明则向上继承**（父表 → 祖父表…取第一个），父子关系复用面包屑那棵树（`find_parent_table`）；
③ 显式声明与继承来的那份**同名主体不同色 → 硬错误阻断**，报错点名是哪张祖先表；
④ 只跟"继承链上**最近的显式声明**"比——否则 L1 声明 / L2 未声明 / L3 反色会被漏掉；
⑤ 声明过的主体**即便本表没用到也进图例**（子图图例是全集、跨层同构）；⑥ 部分声明时其余主体从**未占用档**取；
⑦ **不声明则与从前逐字节相同**。写错一律拦下（未知色名报可用色名 / 撞色 / 同主体两色 / 缺 `=`）。

**影响**：`table_to_dsl.py`（`COLOR_NAMES` / `parse_color_map` / `resolve_colors`）、`build.py`、`flowtable-spec.md` §2、`gates.py`。

## D-50 drawio 的权重：改几何只影响 html，改走向才动流程表

**背景**（用户："drawio 的定位是流程表和 html 的配套产物。**只有当用户主动修改 drawio 的时候，它的权重才会增加**。"）：
drawio 不是第二份事实源，但用户确实会在里面动手。它的权重该随"动了什么"而变，不能一刀切。

**结论**：① **只改几何**（拖节点、调线条）→ 只回流到 `flow.yaml` → **只影响 html/drawio 的布局，流程表一个字都不动**；
② **改节点走向**（拓扑）→ 那是在改事实源，必须能回写流程表，且**冲突时默认拦截**（D-45），`--force` 才放行；
③ 语义列（节点名/主体/执行人/时间）**一律以流程表为准**，在 drawio 里改名**不回写**——要改名就改流程表，
走向是唯一例外，因为它只能由图重建；
④ 几何改动必须**有出口**：`build.py` 默认复用 `flow.yaml` 几何（保护手工微调），
所以 drawio 的几何要经 `sync` 回流才会进产物——直接 build 不会读 drawio，这是正确的路径而非"改了白改"。

**为什么分这么细**：几何改动若偷偷改表，用户"拖一下框"就丢了自己的语义编辑；
走向改动若被静默吞掉，用户"改了图"却看不到表变，会以为同步坏了。**两头都不能越界。**

**影响**：`sync.py`、`writeback.py`、`gates.py`（`_check_drawio_weight`）、`flowtable-spec.md`、`SKILL.md`。

## D-51 产物命名：`<流程名>-flow.*`，流程名取目录名或表名

**背景**（用户："为什么这个命名是 flow.html 而不是 flowchart-skill-flow.html"）：产物一律叫 `flow.*`
就把名字丢了——四层子图一起交付时，收件人拿到四个都叫 `flow.html` 的文件，只能靠文件夹名猜。

**结论**：① 产物名 = `<流程名>-flow.{yaml,html,drawio,manifest.json}`，四份共用一个前缀；② 流程名取
**目录名**（表名是约定名 `flowtable` 时）或**表名**（否则）——`flowtable.md` 不承载语义，身份在目录上；
③ 规则只有一份（`artifact_stem`/`artifact_rel`），`build`/两个 `render_*`/`manifest`/`sync`/验证层
**全部复用它**，不各拼各的；④ 下钻链接与面包屑都由**流程表**路径换算（`subflow_target` 只返回流程表）；
⑤ 表名非约定名时 build 打印一行说明按什么取名——不让人猜。

**为什么不用 `--name` 参数**：名字该由事实源自己带出来，不靠人每次记着传，漏传就退回无名。分叉的代价
实测过：`sync --apply` 落 `flow.yaml` 而 build 读 `<名>-flow.yaml`，手工调的几何在 apply 后凭空消失、无报错。

**影响**：`table_to_dsl.py`、`build.py`、`sync.py`、`render_html.py`、`render_drawio.py`、`semantics.py`、`verify/_lib.py`、`gates.py`。

## D-52 单文件交付：子图内嵌为主 html 的"视图"，下钻切视图不跳页

**背景**（用户："我发给客户就是只发一个 flow.html 文件……类似于 PPT"）：下钻原本靠"跳到子目录里另一个
html"，交付物就必然是一堆文件加文件夹；另存 / 转发 / 拖进邮件任一步漏了子目录，下钻变 404——越有用越脆。

**结论**：① `build` 只产出**一份 html**，把全部后代子图（递归、**按表**去重）内嵌成 `<div class="view">`；
② 点可下钻节点**切视图**（`data-sub` = 视图 key = 子表流程表的相对路径），不再改 `location`；③ 面包屑与
视窗记忆交给 JS（轨迹按点击栈、视窗键带视图，每层各记各的）；④ 图例取**跨层并集**，同名主体跨层异色是
硬错误（D-49 的跨层版）；⑤ 子表 DSL 缺失时主 build 自动补齐（只补 yaml），补不齐则**静默降级**（不画环、
不给入口）；⑥ **没有后代子图时输出与从前逐字节相同**；⑦ drawio 仍每表一份、只铺一跳——它靠多页承载层级，
不需要合并。

**为什么不是"主图 + zip"**：zip 解压后还是一堆；**不是"全画进一张大图"**：那正是下钻要治的臃肿。

**影响**：`render_html.py`、`build.py`（`_prepare_child`）、`manifest.py`（`_main_slice`：只反解主视图）、`gates.py`。

## D-53 落盘通道冲突：端口按边类型分流处置（loop/jumpR 重规划，spine/horiz 保留手调）

**背景**（2026-09-13 审查发现）：手落盘的 `gapx/gutter/channel` 是"用户微调过"的几何提示，重渲染优先
沿用（D-28）；但换过列布局/端口后提示会过期，冲突检测判下就得作废。原做法把**通道与端口一起丢掉**再重
规划——而 `pend` 只收 `loop/jumpR`，`spine/horiz` 丢了端口就没有第二次机会，只能回落默认路径。

**结论**：① 冲突时一律清 `gapx/gutter/channel`（通道是冲突主体，留着必共线重叠）；② 端口 `exit/entry`
**按 kind 分流**：`loop/jumpR` 会被 `pend` 重新推端口 → 清掉旧的（留着会带偏候选）；`spine/horiz` 没有
重规划出口 → **保留**用户手调的端口；③ 顺带去掉 `loop` 左族候选的重复追加（不影响命中结果，纯去噪）。

**为什么不是"一视同仁全清"**：spine/horiz 清了就白扔手调；**不是"全保留"**：loop/jumpR 重规划会读到
过期端口，推出的候选被带偏——两类边处境不同，待遇就该不同。

**影响**：`router.py`（`_ensure_gutters` / `_candidates`）；几何对既有产物**零变化**（幂等不变式守着）。

## D-54 跑马灯环外扩 4px：与边框重合在通道与动画两层都不可行

**背景**（2026-09-13，用户问"环为什么不与节点边框重合，而是外扩一个 OFFSET"）：D-47③ 只记了"用运动通道、不用描边/角标"的结论，"为什么不能直接共用边框"的理由没落盘。

**结论**：环是**独立元素**，形状按等距外扩 4px 生成（菱形逐顶点 / 椭圆 rx·ry / 矩形四边各 +`SUB_RING`）——不是 scale，scale 会让长短边扩出不等的距离。
① 描边通道已满载（颜色=主体、虚线=⚠，visual-spec §1），且一个元素只有一个 `stroke-dasharray`：⚠ 的静态 `6 4` 与跑马灯的 `14 6`+`dashoffset` 动画互斥，共用边框两头互相吃；
② 动画冲突：`sub-march-glow` 的呼吸（opacity 0.4↔1）会带着主体边框忽隐忽现，hover 加粗（2→3px）会让环外跳半像素；
③ 降级可辨识：reduced-motion 下环退化为静态虚线，与边框重合就读不出"另一圈、可点击"——下钻入口的可见性是这个功能的生命线（D-47④ 同理）。

**为什么是 4px**：边框自宽 2px 之上，"贴太近与边框糊成一体"与"太远压到相邻节点/连线"之间的实测平衡；环 `pointer-events:none`，点击区仍是节点本身。

**影响**：`render_html.py`（`SUB_RING` 常量与三种形状的 halo 生成）；对几何门禁零新增项（环不参与碰撞检测）。

## D-60 本机 git 的 ref 写入被沙箱静默拦截

**现象**：`git checkout -b` 打印"Switched to a new branch"但 `refs/heads/<branch>` 并没建（分支实为
unborn，此时 commit 会落在无父的孤儿根提交上）；`git commit` 打印成功、commit 对象也真的入账，
但 ref 更新静默失败，ref 文件被那次失败的重命名删掉；`git update-ref` 同样无效。**最重的一档**：
被删掉的是**已存在的** ref 时，`HEAD` 退回 unborn——`git branch -vv` 只剩别的分支、
`git status` 把全部文件显示成 `A`（看着像"整个仓库都是新增"），而提交对象其实完好。
**为什么**：git 更新 ref 走"写 `.lock` → rename"两步，这个原子重命名在本机沙箱内被拦；
而直接写 `.git/refs/...` 文件本身是放行的。
**结论**：任何 git 写操作后都要显式复核 `git rev-parse HEAD`；ref 没落盘（或已被删）时，
先 `git rev-parse <提交短哈希>` 取全哈希（对象还在，不依赖 HEAD），再用 Write 工具写
`.git/refs/heads/<branch>` 补回，最后复验 `HEAD` / `%P` / `branch -vv` / `status --short` 四项。
本仓库原先没有任何提交身份（commit 直接 fatal），已补设 repo-local
`user.name=WorkBuddy` / `user.email=workbuddy@local`，与既有提交作者一致。
**影响**：本机所有做分支/提交/变基的会话——"命令报成功"不等于"ref 已落盘"，不能当信号用；
`status` 里满屏 `A` 是同一个坑的假象，别误判成"文件都丢了"。

## D-61 同侧错峰槽位硬上限 2：第 3 条起静默留空 → 掉头折返

**现象**：节点同侧「1 条入边占住侧中线 + ≥2 条出边」时，第 3 条起错峰静默留空（`sdye` 不写）→ 锚点落回侧中点 = 入边锚点 → 出边首段把入边末段原路画回来，`validate` 报「掉头折返」。自举产物一次暴露 10 张表；44 条／23 条是同一缺陷在两个时刻语料上的两个数，都对。

**为什么**：`_place_offset` 的候选 `[0] + [s·k·step, k=1..5]`（`step=2×细格`）被 `lim = 半边长 − 细格` 裁到只剩 `k=1`，而 `taken` 同时装着「入边锚点」与「先排的同类出边」→ 本侧槽位硬上限 = 2 且符号固定，用尽即静默空手而归。**与 D-15 的时序无关**：`stagger_source_anchors` 确实跑在端口定案之后。

**结论**：`_place_offset` 分两趟——第一趟**一字未动**（能成的地方一个字节不动）；第二趟**仅在 `0 ∈ avoid`（= 折返条件）**时触发，只跟**入边锚点**避让，允许与同类出边共槽。语义分界：**压入边锚点 = 硬错误（折返）**，与同类出边共槽 = 出边首段共线（分叉，`validate` 本就豁免）。

**影响**：`geometry.py`（`_place_offset` 增参 `avoid`、+7 逻辑行）；`router.py` 一行未改。四面全绿、`equiv` 58/58 相同、既有产物逐字节不变、99 份 yaml 扫荡 87 不变 / 12「有错→无错」。
**已知边界（不堵）**：`avoid` 含 `0` 与 `±20`（须手填 `dye`）时第二趟仍可能无槽——语料 249 个同侧节点 `avoid` 全是 `{0}`，且**非静默**，门禁会拦。

## D-72 流程表扩到 12 列：字段登记表 + ICOM 序 + 显性判定

**曾这么定**：9 列，列下标硬编码散在 6 个文件十几处；「输入 / 输出」只作为**手册**里的两列存在（流程表里没有）。

**为什么改**：① 手册的列应当是**流程表列名的投影**，不该凭空发明两列——否则同一件事有两个说法；② 按维度完备性排，**输入/输出比「行动所需时间」更普遍**
（每个节点都有进出，时限只对任务成立），而后者早就占着一列；③ **IDEF0 的 ICOM 与乌龟图（IATF）**都把「输入 · 依据 · 输出 · 机制」当作一个活动的四支箭头，

**结论**：① 12 列 `阶段 | 编号 | 名称 | 类型 | 输入 | 依据 | 输出 | 主体 | 执行者 | 行动所需时间 | 下个节点 | 描述`，**列序即 ICOM**；② 字段的层级 / 来源 /
显性判定 / 渲染去向 / 校验写进 `flowtable-spec.md` §2 的**字段登记表**（`flowtable.COLUMNS` 是它的代码镜像，全仓列下标一律取自它）；
③ **显性判定**：某列全表都是 `—` ⇒ 本表对它隐性（不要求填、不进悬浮框）——自举表的时间列正是这个情形；④ `依据` 与 `⚠` 咬合：
写得出来写依据、写不出来打 `⚠`、两个都空由 H7 软提示点出（**只对判断节点报**）；⑤ 执行人→**执行者**、行动时间→**行动所需时间**；⑥ 新增 **H9 主表列名校验**。

**影响**：`flowtable.py` / `flowtable_check.py` / `writeback.py` / `xml_reader.py` / 两个渲染器 / `table_to_dsl.py` / `selfboot_gen.py`、

## D-74 节点类型规范化：四种类型、三个形状

**曾这么定**：五种类型（开始/结束/任务/判断/终端子流程），形状 = 椭圆 / 圆角矩形 / 菱形 / 虚线圆角矩形。

**为什么改**：① 「终端子流程」的立论是"结束 = 全流程**唯一**终点"，而这条**没有校验**，样例自己就有两张子表各含两个「结束」；
② 它还制造两处冲突——名字与 `⊞ 子流程` 撞车（一名一物）、形状与任务同形且虚线又和 `⚠` 撞；③ 对照 GB 1526-89 ≡ ISO 5807：
处理符号只有处理/既定处理/判断/并行方式，其余是流线、端点符、连接符、注解符——标准里多出来的那些在我们这儿都由列或标记承载；④ 用户要"左右圆、中间矩形"的端点，椭圆太丑。

**结论**：① 类型四种：开始 / 结束 / 任务 / 判断，「结束」**可以有多个**（每个结局一个）；② 形状三个：矩形 = 过程、
菱形 = 判据、胶囊 = 端点（起止靠入边/出边分），胶囊**几何按矩形算**（drawio 的圆角矩形走矩形周长），三份产物同端点；
③ 并行与排斥的判据是**类型不是标签**：判断 = 选一条（标签是条件、必列全），其余类型多出口 = 全都走（标签只是路线名）；
④ `子流程` → 任务的旧别名一并删；⑤ 图里不写类型属性（承 D-73）。不设类型清单见 `flowtable-spec.md` §2《类型登记表》。

**影响**：`dictionary.yaml` / `semantics.py` / `flowtable_check.py` / 三个渲染器 / `xml_reader.py` / `selfboot_gen.py`、
`flowtable-spec.md` §2 新增《类型登记表》+ 不设清单、`visual-spec` / `dsl-spec` / 模板 / `SKILL.md` / `ARCHITECTURE.md`、

## D-75 子流程记号：叠影卡取代跑马灯

**曾这么定**：可下钻节点在边框外一圈画**流动虚线环**（`SUB_RING=4.0` + `@keyframes`，D-47/D-54），理由是"运动"是当时七个通道之外唯一没被占用的第八个。

**曾这么定**：悬停某节点 → 与它相连的节点/边留亮、**其余压暗到 `FOCUS_DIM = 0.13`**，被悬停节点再加一圈 `drop-shadow` 光晕。

**为什么撤**：① 它在**删信息**——被压暗的节点上，`⚠`/`⚠?` 的橙/红描边、执行主体配色、执行者小字一起退到看不见，
而 `⚠` 恰恰是这张图要用户核对的地方；② 这张图最常见的读法是**静态**的（同 D-75），而悬停是瞬态：
鼠标一移开，读者刚建立的"谁连着谁"就没了；③ 它是**双重编码**——"这一处和它的邻居"已经有加法记号
（描边加粗 + 流光），压暗是同一件事的第二遍，而第二遍是减法的；④ 快速划过一排节点会连续触发几十个元素的
opacity 过渡与强制重排（jank）；⑤ 13% 透明度的灰色小字远低于对比度底线，且触摸屏根本没有 hover。

**结论**：只留两样——悬停节点自己的描边加粗（`.ndg:hover .shape`），相关主干边跑流光（D-80 起是**悬停期间循环**）；
**压暗、`transition:opacity`、`flow-focus`/`is-sel` 两个类、光晕一并撤掉**（光晕与叠影卡抢"节点外围"这一层，
又与描边加粗重复）。边标签不再为悬停携带 `data-ei`：省掉一对"标签 ↔ 边"的配对。原本还有"与它相连的边
加粗成 3px"，D-80 把它也撤了；加粗这一半如今只剩悬停节点自己那一圈——它是**静态**的，「减少动态效果」下仍在。

**影响**：`render_html`（CSS/JS/标签标记）、`visual-spec` §1、`gates.py`（4 条断言换向 + 一条负向守卫）、两份基线重钉。

## D-77 流程布局的画布：贴合内容 + 内容居中

**曾这么定**：画布宽写死在字典（`canvas.width: 1180`），首列中心写死 `DEFAULT_COL_X = 400`，两者互不相干。

**为什么改**：实测主视图内容（含回路通道与标签）只占 200..700 ⇒ 左空 200、右空 480，**整幅偏左 140px**；渲染子表偏 160px——这份产物最常见的用法是**单文件发给同事**，页面比内容宽一倍还不居中，读起来是残的。（泳道没有这个问题：宽度本来就由部门列宽累加算出，流程布局与泳道的差别就在这一处，不必另立规则。）

**结论**：`table_to_dsl` 量一次真 ink（临时 yaml → 引擎跑路由 → 取节点/折线/标签的 x 极值），写两个**派生量**进 DSL：
① `width` = max(内容宽 + 2×边距, 标题块宽 + 2×边距)（引擎仍取 `max(它, 内容右沿+边距)`，写小了会自己撑开）；② `origin_x` =
居中所需的左留白——`Grid` 把它加在**每一列**上、`Router` 把它加在左侧回路通道的基准上。**不写进 `col_x`**：`col_x` 留空有既定
含义（按字典 col_pitch 展开，D-29），写死展开结果等于把列距抄进脚本。平移是刚体运动 ⇒ 第二次跑 Δ = 0，**幂等**。

**副作用**：平移被**归一化**——像素不是终值，挪不动行列聚类的位移不再改产物（"挪节点"夹具因此改成跨聚类位移）；
子表 yaml 已存在时 build 整条跳过，布局规则升级后要让子表跟上得删掉 `*-flow.yaml` 重新生成。

**影响**：`table_to_dsl` / `geometry.Grid` / `router` / `engine` / `dictionary` / `gates` / `dsl-spec` / `examples/README`、两份基线重钉。

## D-78 子流程记号改为「框内内衬线」：出框的记号必然惹三样麻烦

**曾这么定**（D-75）：记号做成**向外**叠的背卡（同形状同色、向右下偏移 5/10px，两张卡两个台阶）。

**为什么改**：向外扩就同时和**端口**、**相邻墨迹**、**包围盒/网格**打交道——实测两条：① 端口在外接矩形的边中点上，
向下的出线与向右的出线**从卡片里钻出来**（用户的原话："锚点还是最内侧的那个端口"）；② 外扩 10px 的包围盒
170×70 是**离格的**。折角/页签/角标换一版也一样，只是换个出框的位置；菱形上最明显——包围盒的四角在形状之外。

**结论**：记号移进框内——同形状、**内缩 2px**、**描边 1px**、**同色 55%** 的一道"内衬线"：端口干净、连线不必改
口径、包围盒与网格一律不动。规格收到 1px/55% 是因为节点高 60、文字两到三行时内圈离文字只剩几像素，
只有退成"里衬"才不跟文字抢。**不再另跑一段光**：悬停沿它转一圈那版已撤（D-80），内衬线只负责"这里有子流程"，
"能点"归悬浮框的灰字提示管。

**影响**：三个渲染器、`xml_reader`（drawio 那圈线仍带 `flowchartSkillSub=1`）、`visual-spec` §1、
`flowtable-spec` §2、`SKILL.md`、`gates.py`（新增"记号必须落在包围盒内"一条）、两份基线重钉。

## D-79 流光改成「两层同一道光」：不用白，用同色系叠出"中间亮、周围渐变"

**曾这么定**：一条加宽的半透明冷色段（`#4a86c8`、宽 5、硬边圆头）沿主干边跑一趟；内衬线的跑光是同色的 2px 硬边段。

**为什么改**：连否两版（白色、白芯）之后去查开源实现（`svg-flow`、ECharts `EffectLine`、AntV X6/G6、GoJS）：
① **没有一家用白色**——白只在**深色**底上发光（svg-flow 默认轨道 `#1a1a2e`、ECharts 的飞线配深色地图），
我们的底是白画布与浅色填充，白在那儿只能"把线擦亮"、读作擦除；② **"中间很亮、周围渐变"是叠出来的，不是渐变**——
折线拐弯处沿路径的渐变跟不上（那要按路径算渐变），而多层段只要共用同一套 `dash` 与时长就自然成一道光；
③ 单层硬边段读作"线被涂粗一段"，两端有切口。

**结论**：两层——**晕**（宽 9 + `feGaussianBlur 2.5` + `stroke-opacity .4`）+ **芯**（宽 3 + 实 + 同色系加深一档）：
连线用流光的蓝（`#4a86c8` / `#2f6fb4`），内衬线的跑光曾用主体色、芯走 `brightness(.72)`。晕的透明度必须写
`stroke-opacity`：动画动的是 `opacity`，写它会连晕一起点满。`.is-run` 只挂晕、芯用**相邻兄弟**选择器跟随，
JS 那套"实线边 ↔ 流光元素"的一对一配对不必改；**两层规格如今只用在连线上**（D-80 撤了内衬线那段跑光）。

**影响**：`render_html`（`_DEFS` 多一条共用模糊、`svg_edge`/`_sub_run` 各出两层、CSS 与时长）、`visual-spec` §1、`gates.py`（+5 条：两层数量相等 · 芯紧跟晕 · 两层不用白 · 晕用 `stroke-opacity` · 模糊只定义一次）、两份基线重钉。

## D-80 悬停只留"一条会动的光"，可点击改由悬浮框用文字说

**曾这么定**：悬停节点 → 与它相连的边加粗成 3px（静态记号）+ 相关主干边跑**一趟**流光（D-76）；可下钻节点的
内衬线上，悬停时另跑一段光沿它转一圈（`.sub-run`，两层同色光，D-78/D-79）。

**为什么改**（用户两次实测反馈）：① 加粗与流光是**同一个意思说两遍**——边上的光已经在回答"哪儿相关"，
而线宽只该由"实线/虚线"这条作者语义决定；② 跑**一趟**是一闪而过，像页面抖了一下，读不出"光顺着流程
一条条走下去"，故改成**悬停期间循环**；③ 内衬线那段转圈光是**第三遍**，"这里能点"该由**悬浮框**在用户伸手去点的那一刻说。

**结论**：① 流光改 `animation:… linear infinite`，**只在悬停期间**（`.is-run` 仍由 JS 开关，离开即摘）；
② `.edge.is-match` 与 JS 打标整段删除；③ 内衬线只剩**静态那一层**（`_sub_run`、`sub-ring-scan` 与常量删掉）；
④ 悬浮框**标题行右侧**加灰字 `（点击查看流程详情）`（`.tt-sub`，11px `#999`），判据是 `d.sub`——与内衬线、
下钻入口同一个真值；正文那句"点击下钻…（Ctrl/⌘+点击…）"只留**不重复**的半句。

**影响**：`render_html`（CSS/JS/提示模板/`_sub_ring` 收参）、`visual-spec` §1、`flowtable-spec` §2、
`SKILL.md`、`gates.py`（3 条换向 + 5 条新增）、两份基线重钉——**drawio / svg 逐字节不变**（装饰只住 HTML）。

## D-81 渲染契约跟产物同进同退：失败时把契约也还原

**现象**：`sync --fresh` 判"《流程表》有没有被直改过"只认契约里的 `source_sha256`（D-69①）。而这个字段由
`table_to_dsl` 在**渲染之前**连同 yaml 一起刷新。于是：改表 → build 在渲染/审核环节失败 → 产物按
"不留半成品"还原成上一版，**契约却已经指向新表** ⇒ 此后 `--fresh` 一律回答"表未变"，stale 门禁永久失效。

**为什么不能只靠"跑成功再刷新"**：`table_to_dsl --write` 单跑（不经 build）也要写出完整契约，否则
`sync --apply` 复制过去的那份会缺基线——刷新点不能后移，只能**补还原**。

**结论**：`build.py` 在 `_gen_dsl` **之前**读下契约的上一版字节（第二份回滚底本），四个失败分支
（转 DSL / 几何 / 渲染 / 两道审核）各还一次（`_rollback_manifest`，原本没有就删掉）。还原后状态自洽且
**看得见**：产物旧、契约旧、yaml 新 ⇒ 任何消费者都会报"契约过期"，不再有静默失效。

**影响**：`build.py`（回滚底本 + 4 个失败分支）、`gates.py`（`产物审核不过` 那节加两条：契约逐字节还原 ·
失败后 `source_stale` 仍是 `changed`）、`visual-spec` §4.1（"不过就还原"补上契约这一半）。

## D-82 泳道跨趟：本趟自动设下的 `sdye` 也要还回去

**现象**：引擎重建布局（探布 → 定案，D-39）时对旧布线器只调 `release()`。端口、`dye`、"挪到空闲侧"三样都在
`_reset()` 里还，唯独**错峰 `sdye` 没还**——它是 `stagger_source_anchors` 在构造期直接写进边对象的。于是
第二趟把上一趟的自动偏移当成"手填值"（对手填值一律让路），D-31 的孤儿复查护不住它。

**为什么不能并进 `_reset()`**：`_pre_route()` 里也调 `_reset()`，而那时的 `_stagger_set` 正是本趟刚设下、
还要用的偏移——并进去会把本趟的错峰当场清掉。

**结论**：`release()` 里**清掉本趟自动设下的那批** `sdye`（`_stagger_set` 里的 id 一律 `pop`），**不是**
"还原成原值"——原值可能就是上一趟的残留（实测探布趟写下的 20 / −20 会一路活到定案趟）。手填值本来就不进
`_stagger_set`，所以清它既不碰用户填的、也不留残留。实测：600 个随机泳道图里 6 个会留下"端口只剩一条边、
却仍带自动偏移"的菱形出边（锚点被从顶点推到斜边），修后为 0。

**影响**：`lane_router.py`（`release()` 清 + `_reset()` 不动）、`gates.py`（新用例：自动的清掉 · 手填的留着）、
`swimlane-spec` 的 `route_left` 行（跨趟还什么的口径补一句）。

## D-83 图不完整要当"仪器故障"，不许当成"覆盖率挺高"

**现象**：`fn_graph` 遇到读不动的文件只记一条 `stats.parse_errors`，那个文件的函数**一个都不进分母**
⇒ 把某个模块改成语法错误，`coverage.py` 反而报 `100%` 通过、退 0，七门全绿（实测复现）。

**为什么不能算覆盖缺口**：缺口的修法是"去补表"，而这里的修法是"去修图"——两者混在一档会让人去找
根本不存在的缺失函数。`coverage.py` 的 0/1/2 契约里，2 正是"输入读不了"，与"图/目录不存在"同一档。

**结论**：① `fn_graph` 的 `files[*]` 记录加 `unparsed: true`，让消费方能区分"真没函数"与"没读动"；
② `coverage.py` 读到 `stats.parse_errors` 非空即打印逐条明细并**退 2**（`accept.py` 门③ 已有的
"退 2 = 仪器故障"分支原样接住，不必改门）。

**影响**：`dev/tools/fn_graph.py`（记录加标记）、`dev/tools/coverage.py`（读 + 退 2）、
`dev/coding-spec.md`（G1 之外新增一条仪器口径）、自举基线重钉（`fn_graph` 改了要重跑生成器）。

## D-84 审查批二：说了 ✗ 就得有人听；反查要看得见形状；口径不许有两份

**现象**：① `writeback` 打印"✗ 回写结果未过结构校验"却仍 `return 0`，`sync --apply` 据此把那份表原样覆盖进
《流程表》——判词没人听；② `xml_reader --diff` 把回写那一步的输出重定向进 `StringIO` 后丢弃，✗／冲突／⚠ 三类
告警一个字都没露；③ 契约里的 `by_type`（连同标签边/回路/⚠ 三个计数）只有 `summary()` 在用、从不参与反查
⇒"把判断节点画成矩形"能全绿通过（几何自检按产物自称的形状反推类型，永远自洽）；④ 同一份 `.drawio` 在
`manifest` 里有两种读法（`utf-8` / `utf-8-sig`）；⑤ 渲染期非 `ValueError` 的异常绕过还原。

**结论**：① `write` 返回"自检是否通过"，`sync` 与 `writeback.main` 据它定退出码（`--apply` 覆盖不了不合格的
表）；② `xml_reader` 把缓冲里的 ✗/⚠ 逐行露出来；③ 新增**形状反查**（字典 shapes 的 type→shape ←→ 产物里读回
的形状分布），读不出或缺映射都显式报错——顺手修 `_html_shape` 不认胶囊的旧毛病（端点也是 `<rect>`，靠 `rx`
才分得出；不修则新反查当场假红）；④ 两处统一 `utf-8-sig`；⑤ 渲染期任何异常都走同一条还原路；
⑥ `DEFAULT_COL_X` 两份合并回 `geometry`。

**影响**：`writeback` / `sync` / `xml_reader` / `manifest` / `build` / `table_to_dsl` / `flowtable_layout` /
`selfboot_gen`、`gates.py`（形状 mutation 一条）、两份基线重钉。"回写自检为假"那条路没有夹具——见 G10。

## D-85 自产 / 外部按**身份戳**判，不按外壳；判定不许"报告短于清单"

**现象**：① `xml_reader` 只按 `<object>` 外壳判"自产"——外部图被 drawio 加过 link / Edit Data 也是
`<object>`，于是它被当成自家产物：既按 cell 顺序排（而非几何），又把"没有语义、须补进《流程表》"的告警
吃掉；② 外部图的节点名取**整段**标签（含第二行=执行者），与文件头"名称只认第一行"不符；③ `equiv` 一侧
setup 失败即 `return`，其余 59 条用例既不跑也不留条目，而 `all_same` 只看"有没有 False"——报告短于清单
看起来像全过；空清单同理恒判全相同。

**结论**：① 渲染器给每个节点 style 末尾盖 `NATIVE_MARK`（`flowchartSkillNative=1`，与既有
`flowchartSkillBg`/`flowchartSkillSub` 同一套约定），回读按它判自产；外壳仍一律**认领**（否则外部

③ setup 失败逐条补"未执行(仪器故障)"（报告条数恒等于清单条数，退出码仍 2），空清单显式判仪器故障。

**影响**：`semantics`（三个标记的家）/ `render_drawio`（盖戳）/ `xml_reader`（判据 + 名称）/ `dev/tools/equiv.py` / `gates.py`（三条新用例）、drawio 产物与两份基线重钉。

## D-86 交付物③ 补内容；圆角口径以 drawio 的 `arcSize` 为准

**曾这么定**：`render_svg` 只画"名称 + 主体·执行者"一行、不画 `⚠` 两档虚线、不画边标签；`shapes.*.arc`
（值 6）在三份产物里各按各的意思用——drawio 当 `arcSize` 百分比、html/svg 当 `rx` 像素。

**为什么改**（用户拍板）：① "朴素可编辑中间态"里的朴素指没有交互与动画，**不是内容可以少**：交付物③ 单独
发出去时，判断节点分出"是 / 否"两支却看不出分支条件、`⚠` 那几处看不出要核对，等于读不全；② 同一个数一边
当百分比、一边当像素，同一形状三份产物圆角差一倍多（160×60：3.6px vs 6px）。

**结论**：① `render_svg` 补齐三样：节点三行（`t1`/`tm`/`tt2`，与 `semantics.node_lines` 同源）、`⚠` 两档
虚线描边（`pending_style`）、边标签（`<g class="elab">`，几何复用 `L.label_box(e)`）；② 新增
`geometry.arc_px(shp, w, h)` 做百分比→像素换算（胶囊除外：圆角是半圆 `h/2`，D-74），html 与 svg 都走它，
drawio 原样写 `arcSize`——**以 drawio 为准**；③ 字典注释与 `visual-spec` §1 写清"上表每一行三份产物都要画"。

## D-87 `--apply` 覆盖前留底：重渲染失败要把《流程表》还回去

## D-90 子视图没有箭头、悬停没有流光：定义落在视图里、配对用了带前缀的 id

**现象**（用户报"子流程依旧没有箭头、流光也没有"，主图一切正常）：切到任一子视图（`#parts/…`），**一条箭头都没有**，悬停也不亮流光；**只有子视图如此**（主图与单页产物都好）。

**根因**（两条都落在"只在真实文档里才成立的解析规则"上）：① 每张图的 `<svg>` 里各写一份 `<defs>`（8 份同 id）。`url(#ar-main)` 按 id 解析，浏览器只认文档**第一份**，而第一份属于**主视图**——切到子视图时主视图 `display:none`，那份定义随之不渲染，子视图于是全无箭头；滤镜 `soft-glow` 同理，坏了会让流光的**晕**层整层不画（`.is-run` 正挂在晕上）。② 悬停配对拿节点的 `data-id` 去比边的 `data-from/to`，而子视图里前者带 `视图key::` 前缀、后者不带（前缀是给 TIPS 防跨表重号用的）⇒ 永远不相等，悬停什么都不亮。

**结论**：① 定义只留一份，放进**所有视图之外、之后**的一只 `0×0 <svg class="vdefs">`；② 节点另加 `data-nid`（DSL 原始编号）专供悬停配对，`data-id` 继续当 TIPS 的键。**"之后"是硬约束**：marker 自带 `viewBox="0 0 10 10"`，放前面会让 `manifest._html_canvas` / `shot.py` 取到的"第一个 viewBox / 第一个 `<svg>`"变成它——画布被读成 10×10，build 的产物几何自检当场 64 项"越界"退非 0（实测）。

**影响**：`render_html`（`_defs_block` 提到 body 末尾 / `svg_node` +`data-nid` / 悬停配对读 `data-nid`）/ `gates.py`（+3 条：定义一份且在视图之外之后 · `data-nid` 与边同口径 · 晕层滤镜在；另修掉一条被新属性挤掉的前置正则）/ `visual-spec` §1 两行 / 两份基线重钉。**教训**：上一轮的复核是"把 svg 从 html 里抠出来单独渲染"——量不到本条（抠出来后文档里只剩一张图，定义在视图内也照样生效）；**复核必须走真实页面**（带 hash 的 iframe + 截图）。

## D-106 能力陈化：产物盖上"哪一版机制产的"，消费端喊、`check` 拦

**改了什么**：新公共层模块 `scripts/capability.py`（44 模块了）出**两个指纹**——`code` = `scripts/*.py` + `dictionary.yaml`（机制：它改，产物字节会变）· `rules` = `references/*.md` + `templates/*.md`（判据：产物不变、**AI 的判断会变**）。`ledger.py` 在账本顶层盖章（键序 `schema · task · capability · materials · elements`）；`plan.py` 在 `plan.md` 表头写一行 `> 机制指纹：code=… rules=…`（`capability.md_line` 是写与读的唯一出处）；`query.py` / `plan.py check` **只喊不拦**；`capability.py check <产物…>` 硬拦（退 2）。

**为什么**：材料陈化问的是"材料还是当年那份吗"，**问不了"机制还是当年那套吗"**——机制一改，旧账本**一个字节都不变**，它继续被消费而没人知道它按的是上一版判据（各层 `check` 核的都是产物 ↔ 产物，这是"一起错时全绿"的第二种形态）。**不盖时间戳**：§2.4 的幂等要"同输入两次同字节"。
**为什么两个指纹分开**：合成一个就等于逼人二选一——机制变要**回 03 重跑**，判据变**机器产物不用重跑**（判据是给 AI 读的）但人与 AI 写下的结论（计划 / 表 / 澄清答复）值得回看。处置不同，报法就得不同。
**为什么只喊不拦**：拦着读等于不让人取证（"我明知它旧，偏要看一眼"是合法需求）；`--json` 时状态进 `capability` 字段、**不往 stdout 插行**（插了吃这份 JSON 的子代理当场解析失败）。
**射程**（G23）：只盖文件内容，看不见环境（Python 版本 / 有没有 `soffice` / `--encoding` 这类调用参数）。"没漂"不等于"结果对"。

**影响**：`layering.py` 名册 19 / 22 / 3 · `selfboot_gen.py` 阶段表 · 自举树 43 → **44 张表**（基线重钉）· `REPO-MAP` / `README`（**顺带修掉漂了 4 个模块的名册**：写 40/26/17，实为 44/30/19）· `PIPELINE-SPEC` §1.2/§2.1/§2.4/§4/§5.3/§8 · 门⑪ 夹具 59—61。**面① 现在现算核 `REPO-MAP` 名册**（模块数 / CLI 数 / 三层逐个点名）；依赖边数归门⑦（它来自快照）。

## D-108 H10 的"向上找账本"：4 层上限够不着，还把它说成"这次任务没有账本"

**改了什么**：`flowtable_check.find_task_ledger` 从"向上找 4 层"改成**一路找到盘根**（判据仍是最近的先赢，返回 `(账本, 找过的最高目录)`）；`Errors` 长出三个字段 `evidence_checked` / `evidence_ledger` / `evidence_skip`（写在类里，不再靠 `getattr` 兜）；`table_to_dsl._report_checks` 三件事都报准——跑起来了打印**用的是哪本账**（相对本表目录，一眼看出在上面几层）、跳过时说**找到哪儿为止**、`--json` 多一个 `evidence: {checked, ledger, skip}`。

## D-109 `py:oletext` 不再把"另外两种语言"当正文：内嵌 XML 与域代码丢掉并记账

**改了什么**：`parse_legacy` 的 run 判据加**第四道** `_noise_reason`——内嵌 XML（`<标签 …>` 盖住的字数占比 ≥ `max_markup_ratio`，新阈值进 `dictionary.yaml`）与 Word 域代码（`PAGE \* MERGEFORMAT` / `MERGEFIELD 名称 \* MERGEFORMAT` / `HYPERLINK "…"` 这类"域关键字 + 开关"）；丢掉的 run **按理由计数**并写进元素的 `degraded`（"丢掉内嵌 XML 1 条；丢掉域代码 1 条"）。

**为什么**：`py:oletext` 是"按字节捞文本"，它**分不清**正文与文档里另外两种**有自己语法**的东西。那两种长度够、字符也"像字"（`<w:Zoom>100</w:Zoom>` 里全是常用字面），前四道判据全过 ⇒ 混进账本，下游「依据」一引就是一段标签。这条是 D-96 留下的缺口。

**为什么判据要窄**：只认"**有结构证据**的两种东西"；"读起来不像正文"**不判**——那是理解，归 AI（§0.1）。所以 `max_markup_ratio` 能进字典当阈值，而不必靠人逐个盯。

**边界（认下）**：**占住整条 run 才丢**（按比例）。正文里夹一小段标签的情况**不切**——切 = 改字，越了 §1.6 的界；那种情况留给 AI 判读，`degraded` 那条提醒就是为它写的。**流名 / 属性串**（`Microsoft Word 97-2003 Document` 这种）仍可能漏进来：它们没有可判的语法，只有长度——`min_run: 24` 挡掉短的那些，长的照旧靠 `degraded` 提醒。

**影响**：`parse_legacy.py`（`_noise_reason` + `_emit` 计数 + `runs_of` 报数）· `dictionary.yaml`（`legacy_text.max_markup_ratio: 0.25`）· `PIPELINE-SPEC` §1.6 那张表 + 一段边界 · 夹具 **51** 加 `d.doc`（正文 + 内嵌 XML + 域代码，三样用 `\x00\x00` 隔开）：正文留下、两样都不进账本、`degraded` 里两种理由都在。

## D-110 `import_table.py` 加 `--header-row N`：哪一行是列名是**人的知识**，不许脚本赌

**改了什么**：`header_of(text, header_row=None)` 先按 markdown 表切块（`_tables_of`），再判表头；给了 `--header-row N`（1 起，**分隔行不计**）就**按行号取表头**，那一行之前的内容行（分组标题那类）不当数据；写歪了两条路都说清——越界（"第一张表只有几个内容行"）、那一行里认不出关键列（打印那一行原文 + 缺哪一列）。

**为什么**：原来的判据是"**哪一行能认出「节点编号」与「节点名称」就算表头**"——那是个赌。真实的两行表头里，**分组标题行**常写着「序号 / 名称 / 环节」这类词，于是它被当成表头，**真正的列名那行反而变成数据行**（产物里多出一条叫"序号"的节点）。行号一旦由人明说，"表头在哪"就不再是猜；顺带把"两行以上真表头"划出边界（要拼起来才是列名的，先自己在外部表里合并——那是语义活，归 AI）。

**为什么行号按"表内内容行"数**：用户说"第 2 行"指的是**他看见的那张表**的第 2 行。原先边扫边判，行号会跨表悄悄重置；先切表再判，行号才有唯一含义（分隔行 `|---|---|` 也不占行号）。

**影响**：`import_table.py`（`_tables_of` + `header_of` + CLI + 用法）· `references/import-existing.md`（入口 B 的读本：认得的 / 不认的 / 说歪了会怎样）· 夹具 **62** 三条路径（`--header-row 2` 认第 2 行那套列名且分组行文字不进产物 · 越界 · 那一行认不出关键列）。

## D-111 流程清单加第八列「合并/拆分理由」：AI 的并 / 拆判断有了落点

**判据为什么是"非机器组才要求"**：单份材料、或 §4.2 步骤 2 的**强合并**（`重复`/`互补`/`替代`/`被替代`，那是清点卡片上的事实）**不需要理由**——硬要一句只会逼出"因为内容重复"这种废话。只有 AI 自己并的 / 自己拆的才要交代。这也让这一列的两半各归其位：**机器列管事实，AI 列管判断**。

## D-113 规整度 A：验收现场自己收，另给一把清场扫帚

**改了什么**：① `accept.py` **成功即收掉"本次新建的"现场**（进门先记下现场里已有什么、只删增量；没过 / 仪器故障一律留着；`--keep` 留着；`--scratch` 是你给的目录就不动）；清理**在结论印完之后**、`ignore_errors=True`，**永不参与判分**。② 新工具 `dev/tools/sweep.py` 收**存量**（`.accept_tmp/` `.verify_tmp/` `__pycache__/`；**白名单写死**：绝不碰 `output/` 与 `dev/baseline/` 等一手内容）。③ 一次性清场：工作区 **213 MB / 3172 文件 → 68.6 MB / 558 文件**。
