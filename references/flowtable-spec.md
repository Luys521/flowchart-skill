## 2. 字段登记表

节点有哪些字段、各住哪一层、谁来写、何时算"本表显性"、渲染到哪、怎么校验——**一张表定死**。
`flowtable.COLUMNS` 是它在代码里的镜像：**加字段先改这里，再改代码**。

| 字段 | 层级 | 来源 | 显性判定 | 渲染去向 | 校验 |
|---|---|---|---|---|---|
| 项目运作阶段 | 行 | 作者 | 必填 | 泳道行 / 里程碑带 | 非空 |
| 节点编号 | 行 | 作者 | 必填 | 节点 id、边两端、drawio cell id | H2 |
| 节点名称 | 行 | 作者 | 必填 | 节点内第一行 | H7 |
| 节点类型 | 行 | 作者 | 必填 | 形状（菱形=判断…） | H7 / H1 / H4 / H5 |
| 输入 | 行 | 作者 | **显性判定** | 悬浮框 | 软提示 |
| 依据 | 行 | 作者 | **显性判定** | 悬浮框 | **判断节点必填**；与 `⚠` 二选一（见下） |
| 输出 | 行 | 作者 | **显性判定** | 悬浮框 | 软提示 |
| 执行主体 | 行 | 作者 | 必填 | 配色 + 图例 | H7 |
| 执行者 | 行 | 作者 | 必填 | 节点内第二行 | H7（软）；**不得跨主体档** |
| 行动所需时间 | 行 | 作者 | **显性判定** | 节点内第三行 | 格式 `min-max 单位` 或 `—` |
| 下个节点 | 关系 | 作者 | 必填 | 边 + 分支标签 | H3 / H4 / H6 / H8 |
| 节点描述 | 行 | 作者 | 可选 | 悬浮框 | 长度（软）；承载 `★` / `⚠` / `⚠?` / `⊞` 标记 |
| 上游 | 关系 | **派生** | — | 悬浮框 | 由全表的边反推，**不许作者填** |
| 归属组织 / 部门 | 主体 | 配置 | 声明即显性 | 图例 / 悬浮框 | 声明即非空 |
| 主体配色 | 主体 | 配置 | 可选 | 颜色 | hex；跨层一致（D-49/D-59） |
| 归属项目 · 过程所有者 · 版本 | 表 | frontmatter | 可选 | 标题 / 层级索引 | 键封闭（H9） |

**列序即 ICOM**：`输入 → 依据 → 输出 → 执行主体/执行者`——一个节点就是一个盒子加四支箭头
（拿什么 → 凭什么叫 → 交出什么 → 谁在做），后面才是度量（时间）与去向（下个节点）。
判别一支箭头属于哪一类，只问一句：**它被消耗或改变了吗？** 被消耗/改变 = 输入；不被消耗、只决定"能不能做、做到什么程度" = **依据**；动手做它 = 机制（执行主体 / 执行者）。

### 节点类型（类型登记表）

**类型只有四种，形状只有三个。** 形状是类型的可见形式，一个不多一个不少；
`flowtable_check.TYPE_RULES` 与 `dictionary.yaml` 的 `shapes` 是这张表的代码镜像。

| 类型 | 形状 | 结构规则 | 读者读法 | 校验 |
|---|---|---|---|---|
| 开始 | 胶囊 | 无入边；全图 ≥1 | 流程入口 | H1 |
| 结束 | 胶囊 | 无出边；**可以有多个**（每个结局一个） | 一个结局 | H1 / H5 / H8 |
| 任务 | 矩形（圆角） | 出边 ≥1；多出口 = 并行 | 一个处理步骤 | H7 / H8 |
| 判断 | 菱形 | 出边 ≥2，每条**必带标签** | 选一条走（排斥），判据写进「依据」列 | H4 / H7 |

**形状铁律**：矩形 = 过程、菱形 = 判据、胶囊 = 端点（起始与结束靠入边/出边分）。
它让"表 → 图"与"图 → 表"互为逆运算——**表能画对，图能读回**，所以图里不需要任何隐藏属性（D-73）。

**胶囊** = 左右半圆、中间矩形。几何上**按矩形算**：drawio 的圆角矩形走的就是矩形周长，
左右半圆只是外观，端口仍落在矩形边界上——三份产物因此算出同一个端点（D-74）。

#### 并行与排斥：判据是类型，不是标签

| 想表达 | 怎么写 |
|---|---|
| **选一条走**（排斥） | 用 `判断`：出边 ≥2、每条带标签（标签是条件），并**列全每个可能结果** |
| **全都走**（并行） | 用该步骤自己的类型（`任务` / `开始`），几条出口都写上——多出口即并行 |

非判断节点的出口标签是**路线名**（`1→a`、`走A`），不是条件；不带标签同样合法。
自举树里"一个模块扇出到多个函数"就是并行出口。

#### 不设的类型（标准里有、我们不设）

一条理由一个归属——**列、标记或拓扑能表达的，就不设类型**（同一语义不许两处表达）：

| 候选 | 归属 |
|---|---|
| 既定处理 / 子流程 | `⊞ 路径` 声明 + 节点**叠影**；主干视图里内嵌可交互，不占形状 |
| 并行方式 | 多出口本身（见上表） |
| 连接符 / 页外连接符 | 边（含 `回`）+ drawio 多页 / HTML 内嵌视图 |
| 注解符 | 「节点描述」列 + 悬浮框 |
| 输入输出 / 文档 / 数据库 / 显示 | 「输入」「输出」列的取值 |
| 人工 / 自动 / 服务 | 「执行主体」「执行者」列 |
| 延时 / 等待 | 「行动所需时间」列 |
| 里程碑 / 阶段节点 | 「项目运作阶段」列 + 泳道行 |
| 合并（汇合） | 拓扑：多入边；"等齐"还是"谁先到"由**源类型**定（判断来的 = 谁先到，并行来的 = 等齐） |

> 依据：GB 1526-89 ≡ ISO 5807 的处理符号只有四个（处理 / 既定处理 / 判断 / 并行方式），
> 其余是流线、端点符、连接符、注解符；BPMN 五个网关里排斥与并行有明文，包容（OR）由判断的
> 多标签出口覆盖，事件网关与复杂网关不引入。**标准里多出来的符号，在我们这儿都由列或标记承载。**

### 「依据」与 `⚠` 的关系（两个问题，别混）

| 问的 | 谁回答 |
|---|---|
| 这一步**为什么存在**？ | `⚠` / `⚠?`：有出处不标、按常理补的标 `⚠`、推不出要拍板的标 `⚠?` |
| 这一步**凭什么这样做、这样分**？ | **「依据」列**：条款、标准、判据、条件的出处 |

**一条规则咬合它们**：**写得出来就写「依据」，写不出来就打 `⚠`，两个都空 = 你没想过**（软提示点出来）。
所以落表可以「先出节点、后论证」——先写名称、依据留空，到 `05 逐行回看内容出处` 回头补；补不出就转成 `⚠`。
**判断节点的「依据」最要紧**：它就是分支标签背后那条判据（"资料齐全？"的齐全清单），全表最该被追问的一处。

### 「主体配色」小节（颜色是一个体系，见 D-49/D-59）

**颜色怎么取不重要，跨层一致才重要。** 主图「机器」是蓝色，子图「机器」就不能是红色——
同一个执行主体在两个层级有两种颜色，等于**同一个身份有两张脸**。所以配色以**独立小节表**声明：

```markdown
## 主体配色

| 执行主体 | 颜色 |
| --- | --- |
| 用户 | #dae8fc |
| 机器 | #ffe6cc |
```

| 规则 | 说明 |
|---|---|
| 写在哪 | 正文「## 主体配色」小节（配置区），在「## 流程表」之前；**缺省可整节省略** |
| 写什么 | **hex 颜色值**（`#RGB` / `#RRGGBB`），格式不对会被拦下（D-59 由颜色名改为 hex） |
| 继承 | 子表**不写**（整节省略）就沿父表 → 祖父表向上取第一个声明；父子关系与「← 返回主图」面包屑同一棵树 |
| 冲突 | 本表显式声明与继承来的那份**同名主体不同色 → 硬错误阻断渲染**，报错点名是哪张祖先表 |
| 图例 | 声明过的主体**即便本表没用到也进图例**——子图图例是主体全集，跨层同构 |
| 部分声明 | 只声明一部分时，其余主体从**未被占用**的色档里自动分配，不会与显式声明的撞色 |
| 不声明 | 整节省略 = 按各表出现顺序自动分配 |

**为什么是 hex 而不是颜色名（D-59 反转 D-49 的取值形态）**：hex 同样是**可判等的值**，
跨层一致检查照旧由脚本做（字符串相等，还少一层"名字 → 色板"的间接）；配色表因此可以
自由扩展列（描边 / 图标…），不受固定色板约束。继承逻辑不变。

**为什么必须继承**：子表常常只用得到一两个主体。若各表按自己的出现顺序分配，
主图四个主体里「机器」排第 3 拿到橙，子图只有「机器」就会拿到蓝——**下钻一次就换一次身份**。

**写错一律拦下**（不是静默回退）：hex 格式不合法、两个主体撞色、
同一主体声明两种颜色、缺 `=`。写错却静默按默认跑，用户看到的是"我声明了怎么没生效"，极难自查。

**一致性由脚本查**（`table_to_dsl.py`）：比对的是"继承链上**最近的显式声明**"，不是直接父表——
否则 L1 声明 / L2 未声明 / L3 反色这一段会被漏掉。门禁用例见 `dev/verify/gates.py` `_check_color_contract`。

### 节点编号的写法

编号是**插入编号**：`04a` 读作「04 与 05 之间插入的第 1 个节点」，**不是**「04 的第 a 个分支」。

- 主干用纯数字，按流程顺序递增：`01`、`02`、`03`…
- 需要在两号之间补节点时挂字母后缀：`04a`、`04b`（**不把后面的编号整体 +1**）
- 后缀只允许**单个字母 a–z**，即同一位置最多 26 个插入项；不支持 `10aa` 这类两级后缀
- 编号一律**当字符串**处理：它只表示身份，**不承载流程顺序**；任何地方都不得按编号大小排序或比较

**为什么用插入编号**：编号同时被「下个节点」列反复引用、又作为 drawio 里的 cell id 使用。增删节点是常态，若采用"插一个就全体 +1"，所有已有引用会集体失效，用户在 drawio 里按 id 挂过的几何也会错位。插入编号把一次增删的影响限制在**一行**——这是它唯一的、也是决定性的好处。

### 「下个节点」写法

- 单链：`→03`
- 无出边：`—`（**只有「结束」能填**——结束禁止出边，一张图可以有多个结束：每个结局一个）
- **多个出口**：每个出口写成 `标签→目标`，出口之间用 **`｜`** 分隔。例：`通过→13 ｜ 不通过→回 11 修正`（取自 `examples/workflow/` 的节点 12）
- `回` 表示回环（回路），渲染为虚线并走左侧通道
- 判断节点**必须列全每个可能结果**（对应 H4），且**每个出口都要带标签**

#### 为什么分隔符是 `｜`，以及为什么必须有

**任何节点都可能有多个出口，不只是判断节点。** 任务节点同样可以一对多（如"分派登记"之后按来源走两条不同的处理路径）。所以"多个出口要用分隔符隔开"是一条**通用规则**，不是判断节点的特权。

**`｜`（U+FF5C 全角竖线）是唯一的分隔符**，理由：

| 候选 | 为什么不用 |
|---|---|
| `；` / `;` | **内容字符**——会出现在标签和编号后的注解里（`回 10 重编；需技术复核`）。一并当分隔符，脚本就无从判断边界在哪 |
| `<br>` | HTML 标签。markdown 渲染成换行，**读渲染后的表时看不到分隔符本身**，只看到"莫名分了两行"；语义上也不是数据分隔符 |
| 真换行 | markdown 表格单元格放不下 |

解析器仍**兼容读入** `<br>` 与真换行（外部 drawio 回读、历史文件需要），但**写出一律用 `｜`**。

> **把分号当分隔符会被当场拦下**（H3）：`通过→05；不通过→06` 会被解析成**一个**出口、静默丢掉第二条，
> 所以宁可报错也不要它悄悄丢数据。判据是"分号后面还跟着 `标签→目标`"——
> 注解里的分号（`不通过→回 11 修正；需技术复核`）不受影响，那是合法写法。

### 「节点描述」的 `⚠` 前缀（AI 推断留痕）

**AI 推断出来的内容，描述必须以 `⚠` 开头。**

判定标准：这一行/这一条分支的依据**不来自原始材料**，而是 AI 按常理补的——原文没写走向、缺执行者/时限、表述存疑、条款无依据。典型场景是从合同、白板、散表提炼时材料本身有缺口。

以 `examples/workflow/` 的节点 12 为例——假设材料没写清"校验不通过时怎么办"，落表就长这样：

```markdown
| 结构校验 | 12 | 结构校验？ | 判断 | 脚本 | table_to_dsl.py | — | 通过→13 ｜ 不通过→回 11 修正 | ⚠ 材料没写校验不过时怎么办，此处按常理补"回上一步修正" |
```

**为什么必须落在描述里**：本 SKILL 的定位是「高级 mermaid」——AI 独立完成提炼与渲染，**用户只对最终渲染图负责**。所以不确定的地方必须画在图上：以 `⚠` 开头的节点渲染成**橙 + 疏虚线**，以 `⚠?` 开头的渲染成**红 + 密虚线**（两档在图上分得开，否则用户看不出哪几处要自己拍板），悬浮框首行分别显示「此处为 AI 推断，原文未载明」与「此处必须业务方拍板：AI 推不出，且不同选法后果不同」。用户看图时一眼就能看到该重点核对哪里。

- `⚠` 只写一次、放最前，后面直接写依据与存疑点
- **不要因为拿不准就停下来等确认**（拖慢流程），也**不要静默假设**（骗人）——补 + 打 `⚠`
- 拿得准、有材料依据的内容不加 `⚠`

#### `⚠` 与 `⚠?`：两种"没底"，收敛条件不同

`⚠` 开头有两种写法，**区别不是程度，是收敛条件**：

| 写法 | 含义 | 收敛条件 | 图上 |
|---|---|---|---|
| `⚠` | AI **有依据**的推断：材料没直说，但能按条款/行业惯例/上下文单独推出一个合理值 | **无需提问**，留痕即可 | 橙 + 疏虚线（`pending.stroke`） |
| `⚠?` | AI **推不出、必须业务方拍板**的决策 | **必须问过一次并得到回答**才算收敛 | **红 + 密虚线**（`pending.verdict`）——与 `⚠` 一眼分得开 |

**判据**——同时满足下面两条，才用 `⚠?`：

1. AI 无法从材料、已有条款或行业惯例中**单独找到依据**——不是"懒得找"，是真找不到；
2. **不同选择会导致不同的合规、成本或责任后果**——选 A 还是 B，事后的账不一样。

只要有一条不满足（比如惯例里明摆着、或两种选法后果没差别），就还是 `⚠`。

> **为什么必须分开**：`⚠` 原先只有一个标记，担了两种语义，于是**没有收敛条件**——它可以永远留在图上，
> 跟着流程图一路交付出去，用户根本不知道哪几处是"AI 补了个合理的值"、哪几处是"AI 真的在等你拍板"。
> 拆开后，`⚠?` 有了明确的收敛条件（问过一次），交付时能如实报出「仍未决 N 处」（见 `clarify.py`）。

**写法**：`⚠?` 的 `?` 用**半角**（ASCII `?`），紧跟或隔一个空格均可（`⚠?`、`⚠ ?` 都算）。不要用全角 `？`——它会和中文标点混淆，且判定为普通推断。

```markdown
| 裁决 | 02 | 审批口径？ | 判断 | AI | AI | — | 宽→03 ｜ 严→04 | ⚠? 材料未指明按宽口径还是严口径执行，两种走法费用差一倍 |
```

**问的顺序由 `clarify.py` 算**，AI 不必自行判断先问哪个：

```bash
python flowchart-skill/scripts/clarify.py "output/<名称>/flowtable.md"
```

它输出当前**能问的**（frontier）和**要等上游定了才问的**，前者一次问完。规则与理由见该脚本 `frontier()` 的注释。

### 「节点描述」的 `⊞` 标记（下钻子流程）

**一个节点的内部若本身就是一张流程表，在描述里写 `⊞ 子表路径`。**

```markdown
| 渲染 | 06 | 渲染两份产物 | 任务 | 机器 | build.py | — | →07 | ⊞ parts/渲染.md ；一条命令跑六环：结构校验 → DSL → 八项碰撞检测 → … |
```

| 规则 | 说明 |
|---|---|
| 写法 | `⊞` 后跟**相对本表所在目录**的路径，到空白 / `；` / `;` / 行尾为止 |
| 数量 | 一个节点**至多一个**子表——多个会让"点进去看哪个"变成第二个问题 |
| 越界 | 路径**不得逃出本表所在目录**（`../x.md`、`/etc/x`、`C:\x` 一律忽略） |
| 子表本身 | 必须是**一张合法的完整流程表**（有自己的开始/结束，能单独 `--check`、`build`、`sync`） |

**产物名带流程名**（见 DECISIONS D-51）：产物落在**流程表自己所在目录**，名字是 `<流程名>-flow.*`——
流程名取目录名（表名是约定名 `flowtable`）或表名（否则）。所以 `⊞ parts/渲染.md` 对应的是
`parts/渲染-flow.yaml` / `-flow.drawio`：既不是约定的 `parts/flow.*`，也不是按后缀猜的 `parts/渲染.*`。

**HTML 是单文件**（见 DECISIONS D-52）：子图的 html **不再单独产出**，它被内嵌进主 html 作为"视图"，
点可下钻节点是在同一份文件里**切视图**，不是跳页。所以发给客户就发那一个 `<流程名>-flow.html`，
概念上类似 PPT——子目录丢了也不会 404。drawio 仍每表一份（多页承载层级）。

渲染后：

- **HTML 版**：该节点框内有一道**内衬线**（同形状内缩 2px / 1px / 55%，永远在、静态可见、不带动画），
  鼠标移到节点上，**悬浮框在节点名右侧**用一行灰字说明「（点击查看流程详情）」。
  单击**切到子图视图**，`Ctrl/⌘+点击`另开一个窗口并停在该层。
  下钻后左上角出现**面包屑**可逐层点回去
- **drawio 版**：该节点带 `link="data:pageId=…"`，`Ctrl+点击`跳转到同一文件里的**子页**；子页名取子表自己的标题
- **视窗每层各记各的**：滚动位置存 `sessionStorage`，键带"页面路径 + 视图"，
  切回某一层时滚回离开前的位置。大图里若每次下钻回来都被扔回左上角，"刚才看到哪儿了"就丢了

**drawio 只铺一跳，不递归**：每个 `.drawio` 里装「本图 + 它的直接子图」，再下一层由**子图自己的文件**负责
（`parts/l2/mid-flow.drawio` 里装 L3）。这与 HTML 侧形状一致（每层一个页面、一跳一个链接），
且一份流程表**只出现在一个文件里**——若递归平铺，L3 会同时存在于 L1 和 L2 两个 `.drawio` 中，
改一处另一处悄悄过期，属于事实源分叉。三层链的走法是 L1 → 打开 L2 → 打开 L3，逐跳闭合。

**为什么写在描述里而不新增一列**：新增列要动列结构 / 解析 / 全部校验 / 全部模板，
而描述列**已有** `★` / `⚠` / `⚠?` 三类标记语法，加一类是同类里的最小改动面。

**为什么要独立成文件而不是塞进主表元信息**：子表独立成文件后它仍是「唯一事实源」——
可 `--check`、可 `build`、可 `sync` 回写、可再下钻。AI 手写一段静态 HTML 就破了这个原则（改不了、校验不了）。

**降级是静默的**：内嵌不了就**不画叠影、不给入口**，也不报错——
宁可少一个可点，也不能给用户一个点下去没反应的东西。

**只 build 主表就够**：子表的 `<名>-flow.yaml` 若还没有，主 build 会**自动补上**再内嵌（只补 DSL，
不代劳 html/drawio）；补不齐（表不存在 / 结构校验或碰撞检测未过）就走上面的静默降级。
想单独看某一层的 drawio，再对那张子表跑一次 `build`。
主图**不会递归构建子图**——否则主表一改就要重跑 N 张子图，且循环引用会直接死锁。

### 「节点描述」的 `★` 标记（关键点：只标漏看会出错的）

`★` 是**给人看的**路标，一个作用：**告诉读表的人"这一行别跳过去"**。

- **只标那些漏看会出错的节点**：整表通常只有几处。**通篇都标 = 没有重点**——
  样例的子表曾经每行都带 `★`（2026-09-17 修正），等于什么都没说
- 与 `⚠` / `⚠?` / `⊞` **不冲突**：它们各说各的事（`⚠` 是"这条是推断"、`⊞` 是"这里有子表"、
  `★` 是"这条最要紧"），同格时 `★` 排在它们**后面**
- **它不进任何判据**：解析器只认 `⚠` / `⚠?` / `⊞`，`★` 既不影响校验、也不影响渲染

### 分支标签的写法（易错）

标签画在连线上，**控制在 4 字以内**，优先用：`是` / `否` / `通过` / `不通过` / `达标` / `未达` / `中标` / `有` / `无`。

- **布尔判断一律用 `是`/`否`**（或 `通过`/`不通过`）；非布尔的多路分支（按来源、按去向分类）用 2–4 字短词，如 `examples/workflow/` 节点 `14` 的 `有` / `没有`
- 标签过长会撑爆徽章底框、挤占版面，甚至压到相邻节点
- **详细说明一律写进「节点描述」列**，在 HTML 评审版中以悬浮窗展示
- 反例：`从无到有（口头需求/合同文档/表格/图片白板）→11` → 正例：`从无到有→03`，触发形态写进节点 01 的描述
- 反例：`校验通过（H1–H8 全部通过）→13` → 正例：`通过→13`，检查项清单写进节点 12 的描述
- 超过 6 字会触发软提示（**不阻断**），由 AI 自行精简
- 渲染器会沿连线自动避让节点摆放徽章，但**缩短标签始终是首选**——它同时解决挤压和碰撞

## 3. 结构校验规则

命令：`python flowchart-skill/scripts/table_to_dsl.py --check "output/<名称>/flowtable.md"`
退出码 1 = 有硬错误，阻断渲染；仅软提示返回 0。

检查分**三层**，按 ① → ② → ③ 依次跑，范围从小到大：一行 → 一种类型 → 整张图。
分层的意义在于**报错顺序**：① 判错会让后面连错节点、报出一串指向错处的假错，所以必须最先跑；
② 能判的不要拖到 ③，否则「结束节点居然有出边」会被淹在一堆连通性报错里。
H9（表头）不在这三层里——它管的是表格**之外**的元信息区，与三层正交（层 = 运行顺序，H 编号 = 规则主题）。

### 表头层 —— 三区结构的键与值（H9，D-56/D-59）

| 规则 | 含义 | 级别 |
|---|---|---|
| H9 未知键 | frontmatter（id/level/parent/refs/description）与「渲染配置」小节（输出布局/泳道列序）的键封闭——笔误静默忽略 = 整条语义悄悄丢失；报错列出全部合法键 | 硬 |
| H9 语法 | frontmatter 必须是合法 YAML 键值映射（缩进用空格），解析失败连同原因报出 | 硬 |
| H9 条目废弃 | 表头区（frontmatter 之后、表格之前）**不许出现任何 `- 条目`**——布局/配色写配置小节，防两套机制混用 | 硬 |
| H9 refs | `refs` 里每个路径必须真实存在（相对本流程表目录） | 硬 |
| H9 parent 双向一致 | `parent` 声明的文件必须存在，且其中真有一条 ⊞ 指回本表——声明与 ⊞ 漂移当场拦下 | 硬 |
| H9 level 双向一致 | `level` 声明（L0=主流程）必须与 ⊞ 推导深度一致 | 硬 |
| H9 配色 hex | 「主体配色」表的颜色必须是合法 hex（#RGB / #RRGGBB）；跨层同主体异色硬错误 | 硬 |
| H9 派生量禁入 | 「层级号 / 子表清单 / 构建顺序」不收——由 ⊞ 声明派生（`layer_index.py`），手写必漂移 | 硬 |
| H9 空值 | 「refs / parent / level / id」写了键就不能是空值 | 硬 |

### ① 节点层 —— 只看这一行自己写得对不对

| 规则 | 含义 | 级别 |
|---|---|---|
| H2 编号 | 非空、唯一；**数字开头的编号**只允许 `数字 + 至多一个字母`（01 / 01a），`10aa` 会被拦下 | 硬 |
| H7 语义 | 节点名称、执行主体非空；节点类型必须是 开始 / 结束 / 任务 / 判断 之一（四种，见《类型登记表》） | 硬 |
| H7 软提示 | 执行者、行动所需时间可空；**判断节点的「依据」为空且未标 `⚠`** | 软 |

### ② 类型层 —— 只看这个节点与它的出边

每种节点类型"自己必须满足什么"，一张表看全：

| 类型 | 全图个数 | 出边 | 分支 | 级别 |
|---|---|---|---|---|
| 开始 | ≥1（H1） | 必须有 | — | 硬 |
| 结束 | ≥1（H1） | **不许有**（H5） | — | 硬 |
| 任务 | — | 必须有 | — | 硬 |
| 判断 | — | 必须有 | **≥2 个且每个都带标签**（H4）；分支目标不重复、标签不重复（H8） | 硬 |

> 「必须有出边」但不满足，报的是**死胡同**（H8）。
> **任何类型都可能有多个出口，不只判断节点**——多出口之间用 ` ｜ ` 分隔（见第 2 节）。
> 但两者的读法不同：判断的多出口是**排斥**（选一条，所以标签是条件、必须列全），
> 其余类型的多出口是**并行**（全都走，标签只是路线名）。见《类型登记表》。

### ③ 关系层 —— 必须看着别的节点才能判

| 规则 | 含义 | 级别 |
|---|---|---|
| H3 引用完整 | 「下个节点」引用的编号必须真实存在 | 硬 |
| H8 逻辑连通 | 无孤立 / 孤儿（无入边且非开始）/ 不可达（从「开始」走不到）节点；结束节点可达 | 硬 |
| H8 软提示 | 开始节点有入边（回路回到起点属正常，可忽略） | 软 |
| H6 死循环有出口 | 每个有向回路内至少含 1 个判断节点 | 硬 |

> **一个节点只报最可操作的那一条**，避免同一个节点挨两句说的是同一件事的报错：
> - 孤立 > 孤儿 > 不可达，只报最先命中的一条；
> - 结束节点的"没人指向我"专名叫「不可达」，不再叠一条泛泛的「孤儿」；
> - 死胡同由 ② 报、③ 让位；
> - 「下个节点」写了目标但编号不存在时，只报 H3，不再叠一条"没有出边"——
>   否则提示自相矛盾（「下个节点」应为 —，可你明明填了东西）。

> **①②只管"这一行、这个节点写得对不对"，③ 才管"整张图连不连得起来"。**
> 漏填一个「下个节点」、把目标编号写错、或判断的两个分支指向同一处，①② 全过，
> 渲染出来却是一张看着完整、实际走不通的图——八项质量门禁也查不出来（它只管线条与方框，不管语义）。
> 这类缺陷只有 ③ 拦得住，所以**填完表必须跑结构校验，不能只看行数对不对**。

编号「按序连续」（01→01a→02…）**不做检查**——编号只是身份、不承载顺序（见「节点编号的写法」），插入编号打破连续观感是常态。

### 证据层 —— **只有这次任务有账本时才检查**（H10）

材料链的产物（`evidence.json`）是「依据」列的事实源（见 `material-to-nodes.md` §6）。这一层核的是
**你引的东西真的存在于账本里**：它从本流程表所在目录**向上**找 `evidence.json`
（任务级产物住成果根，与各 `<流程名>/` 平级；子表在 `parts/` 下也能找到）。

| 规则 | 含义 | 级别 |
|---|---|---|
| H10 引用完整 | 表里出现的每个 element id（形如 `M03#p012`）都必须在账本里存在；报错点名是哪个 id、并给出账本里共几条证据 | 硬 |
| H10 账本读不动 | 够得着账本、但它不是合法 JSON，而表里确实引了 id ⇒ 报"无从核对"（**不可追溯的引用不许交付**）；一句 id 都没引 ⇒ 不报 | 硬 |

**没有账本（纯口头需求、示例表、自举树）⇒ 整层跳过、不报错**——新判据不许误伤合法的旧表。
`intake.md` 的「依据」列走同一条判据（`intake.py check --ledger …`）。

## 4. 软提示的处理

结构校验以 `⚠ 软提示` 开头的行（缺执行者、缺行动所需时间、判断节点缺依据）**不阻断渲染**，但 AI 必须处理：能推断的补上，
推断的依据写进该节点的「节点描述」并以 `⚠` 开头（渲染时虚线标注，用户在图上即可看到）。
